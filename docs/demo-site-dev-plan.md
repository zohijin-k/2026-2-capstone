> ⚠️ **미확보 자료**: 심사표는 100% / 110% / 120% / 130% 구간별 판정을 요구하지만, 공고문에는 **140% 기준표만** 있다.
> **데모 처리 방안**: 140% 건보료 값을 `÷1.4 × 해당배율`로 선형 환산해 구간표를 생성하고, 화면과 코드에 `(데모 추정치)` 라벨을 명시한다. TF 회의에서 보건복지부 소득판정기준표 전체를 확보하면 표만 교체한다.
> 예) 4인 직장가입자 140% = 311,031 → 100% ≈ 222,165 / 110% ≈ 244,382 / 120% ≈ 266,598 / 130% ≈ 288,815

### 2.6 취업지원패키지 — 두배적금과 결정적으로 다른 점

| 항목 | 두배적금 | 취업지원패키지 |
|---|---|---|
| 선발 방식 | **점수제 100점**, 시군별 정원 | **선착순**, 예산 소진 시 조기마감 |
| 서류 보완 | **불가** (미비 시 즉시 제외) | **7일 내 보완 가능**, 미보완 시 후순위자로 교체 |
| 연령 기준 | 2025.12.31. 기준 만 18~39세 | 2026년 기준 18~39세 (1987.1.1.~2008.12.31.) |
| 소득 요건 | 중위소득 140% 이하 | **없음** |

|---|---|

### 3.4 "신청이 어렵지 않게" 하는 장치

1. **조건부 서류 체크리스트** — 근로유형을 고르면 5종 근로확인서류 중 본인에게 필요한 1종만 남는다
2. **발급처 딥링크** — 각 서류 옆에 정부24 / 건강보험공단 / 4대사회보험 정보연계센터 바로가기
3. **자동 계산** — 전입일·취업일만 입력하면 거주기간·근로기간을 공고일 기준으로 역산
4. **자주 틀리는 것 인라인 경고** — "등본 아닌 **초본**", "사업자등록증 아닌 **증명**", "PDF 암호 해제"
5. **임시저장 / 이어서 작성** — 서류 발급하러 나갔다 돌아올 수 있어야 함
6. **진행률 바 + 남은 항목 수**
7. ~~모바일 대응~~ → **PC 전용으로 확정** (3.5절). 서식 재현을 우선한다
8. **서류별 개별 업로드 + 병합 파일 자동 분리** — 공고문은 "1개의 파일로 압축하여 올려야 함"을 요구한다. 신청자가 7~8개 서류를 직접 합쳐야 한다는 뜻이고, 이 과정에서 누락·순서오류가 생긴다. 데모는 **슬롯별 개별 업로드를 기본**으로 하고, 기존 방식대로 병합 PDF를 올린 경우 **페이지별로 문서종류를 판별해 슬롯에 자동 배정**한다. 배정되지 않은 페이지만 사용자에게 되묻는다.
9. **자동 채워지는 서식1 구간 체크** — 서식1은 거주기간·근로기간을 6구간/4구간 체크박스로 받는다. 데모는 전입일·취업일 날짜만 받아 구간을 자동 선택하고, 선택된 구간을 근거 문장("2021-11-20 전입 → 4년 3개월 → '4년 이상~5년 미만'")과 함께 보여준다. 신청자가 구간을 잘못 고를 여지를 없앤다.

### 3.5 서식 원형 재현 ★

> 신청자가 보는 화면이 **종이 서식과 같은 구조·같은 순서·같은 문구**여야 한다.
> 담당자가 종이 서식과 1:1로 대조할 수 있고, 신청자도 공고문 PDF를 보며 따라갈 수 있다.
> 일반적인 웹 폼으로 재구성하면 이 두 가지가 모두 깨진다.

**맞추는 것 세 가지** — 픽셀 복제가 아니라 구조의 동형성이다.

1. **표 구조** — 좌측 항목 라벨열 + 우측 입력열, 병합 셀 구조
2. **항목 순서** — 서식에 적힌 순서 그대로 (재배열 금지)
3. **문구** — 항목명과 각주(`※ ...`)를 **원문 그대로**. 요약하거나 다듬지 않음

#### 위저드 vs 서식 — 충돌 해소

3.4절의 "단계별 입력"과 "서식 그대로"는 얼핏 충돌한다. **서식1이 이미 절(Ⅰ~Ⅳ) 구조를 갖고 있다**는 점을 쓰면 충돌하지 않는다. 위저드 스텝 경계를 서식의 절 경계와 일치시킨다.

| 스텝 | 서식1의 해당 구획 |
|---|---|
| Step 0 | (서식 상단) 저축목적 · 유사 자산형성사업 참여 여부 |
| Step 1 | Ⅰ. 기본정보 — 인적사항 · 비상연락망 |
| Step 2 | Ⅰ. 기본정보 — 전북특별자치도 거주기간 · 가구 및 소득 |
| Step 3 | Ⅰ. 기본정보 — 근로사항 |
| Step 4 | Ⅱ. 납입금액 · Ⅲ. 입금 받을 계좌 · Ⅳ. 기타사항 |

각 스텝은 **같은 서식의 특정 구획만 보여주는 것**이고, 상단 "서식1 전체 보기" 토글로 한 장 전체가 펼쳐진다. 스텝은 서식을 재구성한 게 아니라 **스크롤 위치를 나눈 것**에 가깝다.

#### 자동계산과 서식 체크박스의 공존

서식1은 거주기간을 6구간 체크박스로 받는다. 체크박스를 날짜 입력으로 바꾸면 서식이 깨지고, 체크박스만 두면 신청자가 잘못 고른다. **둘 다 둔다.**

```
┌──────────────┬────────────────────────────────────────────────────┐
│ 전북특별자치도 │ 최종 전입일  [ 2021-11-20  📅 ]                     │
│ 거주기간      │ □1년 미만 □1~2년 □2~3년 □3~4년 ☑4~5년 □5년 이상   │
│              │ └ 2021-11-20 전입 → 공고일(2026.3.3.)까지 4년 3개월 │
│              │ ※ 전북특별자치도 최종전입일로부터 공고일까지 기간      │
└──────────────┴────────────────────────────────────────────────────┘
```

체크박스는 **읽기전용 + 자동 선택**, 바로 아래 근거 한 줄. 서식의 형태는 보존되고 오선택 여지는 사라진다. 근로기간(4구간)·연령도 같은 패턴.

#### 서식별 재현 범위

| 서식 | 원본 위치 | 재현 방식 |
|---|---|---|
| 서식1 참여신청서 | 시행지침 p13 | 절 단위 위저드 + 전체보기 토글 |
| 서식2 자가진단 | 시행지침 p14 상단 | `점검내용 ǀ 확인·동의` 2열 표 그대로, 예/아니오 라디오. 6번 문항의 하위 ⑨개 제외대상은 접이식으로 원문 유지 |
| 서식3 개인정보 수집·이용 | 시행지침 p14 하단 | 고지문 **원문 그대로** + 동의 체크 2개(일반/고유식별정보) |
| 서식4 제3자 제공 | 시행지침 p15 상단 | 고지문 원문 + 동의 체크 1개 |
| 서식5 행정정보 공동이용 | 시행지침 p15 하단 | 표 그대로 + 서명란 자리에 **캔버스 전자서명** |
| 서식6 심사표 | 시행지침 p16 상단 | **담당자 화면**에 원본 배점표 레이아웃으로 렌더 |

> 서식6을 담당자 화면에 원본 표 형태로 그리는 게 핵심이다. 담당자가 쓰던 종이 심사표와 시각적으로 같으면 학습 비용이 0이고, "자동 채점을 믿어도 되나"라는 저항도 줄어든다. 자동 계산된 점수 칸에 배경색과 근거 문장만 얹는다.

#### PC 전용 고정 레이아웃

**반응형을 하지 않는다.** 폭에 따라 셀을 재배치하면 열 너비와 체크박스 줄바꿈이 원본과 달라져 "종이 서식과 같은 구조"라는 전제가 깨진다. 좁은 화면에서는 가로 스크롤만 허용해 레이아웃을 그대로 유지한다. (서식 폭 940px 고정)

열 너비는 눈대중이 아니라 **원본 PDF의 실제 표 선 좌표**에서 뽑는다. 서식1 기준(표 폭 340.2pt):

| 경계(%) | 의미 |
|---|---|
| 6.3 | 바깥 라벨열 (인적사항 · 가구및소득 · 근로사항) |
| 17.2 | 안쪽 라벨열 (신청자 이름 · 주소 · 연락처 …) |
| 32.4 / 49.2 / 66.1 / 84.8 | 신청자이름–생년월일–성별 행 분할 |
| 28.2 / 57.3 / 67.3 / 81.9 | 연락처 · 비상연락망 행 분할 |

**체크박스 줄바꿈도 원본과 동일하게 고정한다.**

| 항목 | 줄당 개수 |
|---|---|
| 저축목적 · 도 거주기간 | 3 |
| 가구 특성 · 근로유형 · 현직장 근로기간 · 근무처 지역 · 근로형태 | 2 |
| 가구원 수 | 5 |
| Ⅳ. 인지경로 | 흐름 배치(원본이 괄호 안에 늘어놓음) |

**날짜는 년·월·일을 각각 따로 받는다.** 서식의 칸이 원래 그렇게 나뉘어 있고, `<input type="date">`를 쓰면 칸 안에 브라우저 위젯이 들어가 서식 모양이 깨진다.

> ⚠️ **원본 PDF가 2-up 레이아웃이다.** 시행지침·공고문 모두 물리 1페이지에 논리 2쪽이 들어 있다(예: 시행지침 p13에 "- 23 -"과 "- 24 -"가 함께). 서식 캡처·좌표 작업 시 논리 쪽 경계로 잘라야 한다.

### 4.3 OCR 3단계 전략

엔진은 OCR **결과**를 받는 쪽이고, OCR 자체는 현재 **아무도 구현하지 않은 공백**이다. 데모 안정성과 시연 설득력을 동시에 확보하기 위해 3단계로 나눈다.

```python
# demo/backend/ocr/base.py
class OcrAdapter(Protocol):
    def read(self, file_path: str, expected_doc_type: str) -> OcrResult: ...

@dataclass
class OcrResult:
    detected_doc_type: str        # 분류 결과 (engine/config.py 라벨과 일치해야 함)
    confidence: float             # 0.0~1.0
    image_quality: float
    issue_date: date | None
    has_signature: bool | None
    fields: dict[str, str]        # {"성명": ..., "가구원수": "3", "건강보험료": "252,000"}
    bboxes: dict[str, list[float]]  # 판독 위치 → 담당자 화면 하이라이트용
    is_encrypted: bool
    is_screen_capture: bool       # 공고문 "모니터 화면 캡처 불인정"
    page_count: int
```

**"모니터 화면 캡처" 탐지**: EXIF에 카메라 정보가 없고 + 해상도가 흔한 화면 해상도(1920×1080, 2560×1440 등)에 근접하며 + 텍스트 레이어가 없으면 `is_screen_capture = True`. 단, **자동 반려하지 않고 `NEEDS_REVIEW`로 보낸다.** 오탐 시 신청자 피해가 크므로 최종 판단은 사람이 한다.

| Tier | 방식 | 대상 | 데모 필수 |
|---|---|---|---|
| **1. Fixture** | `fixtures/` 샘플 파일 → 사전 정의 판독 결과 | 시연용 8개 시나리오 | **필수** |
| **2. PDF 텍스트 추출** | 정부24·건보공단 발급 PDF는 텍스트 레이어 보유 → `pypdf`로 텍스트 추출 후 정규식으로 문서종류·발급일·가구원수·건보료 파싱 | 실제 PDF 업로드 | **권장** — "진짜 읽는다"를 보여줌 |
| **3. 상용 OCR API** | Upstage Document AI / 네이버 클로바 | 스캔 이미지(jpg/png) | 회의 이후 |

> Tier 2가 실제로 잘 동작한다. 정부24 발급 PDF는 이미지가 아니라 텍스트 PDF다. 암호 해제 여부(`PdfReader.is_encrypted`)도 여기서 바로 잡힌다.
> **판독 실패 시**: `confidence = 0.0` → 엔진이 `NEEDS_REVIEW` 처리 → 담당자 큐로. 데모가 멈추지 않는다.

### 4.7 작성 서식의 PDF 내보내기 (부가 기능)

> **메인 기능이 아니다.** P7(선택)에 배치하고, 미구현이어도 수용 기준(8절)에 영향이 없다.

작성 완료된 서식을 원본과 같은 형태의 PDF로 저장한다.

| 방식 | 내용 | 평가 |
|---|---|---|
| **A. 원본 PDF 오버레이** ★채택 | 시행지침 PDF에서 서식 페이지를 떼어 템플릿으로 삼고, PyMuPDF `insert_text()` / `insert_image()`로 좌표에 값·체크·서명을 그려 넣음 | 결과물이 **원본과 100% 동일**. PyMuPDF는 이미 OCR Tier2 의존성이라 추가 없음. 단점: 필드별 좌표 맵 수작업 |
| B. HTML → PDF | 화면의 서식 컴포넌트를 Playwright / WeasyPrint로 인쇄 | 좌표 작업 불필요, 화면과 항상 일치. 단점: 한글 폰트 임베딩, 헤드리스 브라우저 의존성 추가, 원본과 미세하게 다름 |

**A를 택한 이유**: 이 데모의 논점이 "행정 서식을 디지털로 옮겨도 서류로서 성립하는가"인데, A는 결과물이 기존 서식과 구분되지 않아 그 논점을 가장 강하게 보여준다. 의존성이 늘지 않는 것도 크다.

```json
// demo/fixtures/form_coords/서식1.json
{
  "template": "templates/서식1.pdf",
  "fields": {
    "name":      {"page": 0, "x": 148, "y": 232, "size": 10},
    "birthDate": {"page": 0, "x": 280, "y": 232, "size": 10, "format": "%Y.%m.%d."},
    "gender.남": {"page": 0, "x": 402, "y": 232, "type": "check"},
    "residencePeriod.4년 이상 ~ 5년 미만": {"page": 0, "x": 331, "y": 318, "type": "check"}
  }
}
```

- 좌표는 **논리 쪽 기준**. 2-up 원본은 논리 쪽 단위로 미리 잘라 `demo/fixtures/templates/`에 넣어둔다.
- 서식5의 서명은 `type: "image"`로 캔버스 PNG를 서명란 좌표에 합성한다.
- 데모 구현 대상은 **서식1·서식5 2종만**. 서식5는 전자서명 합성이 들어가 "자필 없이도 서식이 완성된다"를 그대로 보여주므로 시연 가치가 가장 크다.

```
GET /api/applications/{id}/forms/{form_no}.pdf   → Content-Disposition: inline
```

담당자 심사 화면의 서류 탭에 **"작성 서식" 탭**을 추가해 업로드 서류와 나란히 본다. 여기서도 다운로드는 0회다.

## 5. 엔진(진) 측 수정 요청 목록 ★ 즉시 공유 필요

현재 `engine/config.py`는 실제 공고문과 **불일치**한다. 데모 착수 전 정렬이 필요하다.

| # | 현재 엔진 값 | 공고문 실제 값 | 영향 |
|---|---|---|---|
| **E1** | 필수서류에 `"주민등록등본"` | **주민등록초본** (공고문 명시: "※등본 아님") | 라벨 자체가 반대. 최우선 수정 |
| **E2** | `"소득금액증명원"`, `"건강보험료납부확인서"` | 소득재산 증빙 **3종**: 건강보험료 납부확인서 / 건강보험 자격확인서 / 건강보험 자격득실확인서 | 필수서류 목록 재정의 |
| **E3** | 근로확인서류 없음 | **5종 중 택1** (조건부 필수) | `RequiredDocumentSpec`에 "택1 그룹" 개념 필요 |
| **E4** | `"행정정보공동이용동의서"` 서명 필요 | 동일 (유일하게 일치) | 전자서명 대체 시 `has_signature` 판정 방식 협의 |
| **E5** | `DOCUMENT_ISSUE_CUTOFF = 2026-08-01` | 두배적금 **2026-03-03**, 취업패키지 **2026-01-01** | 상수 교체 |
| **E6** | `income_decile` (1~10분위) | 실제 기준은 **중위소득 %** (건보료 고지금액 → 가구원수 대조) | `Applicant` 스키마 변경 필요 |
| **E7** | `INCOME_DECILE_LIMIT = 9` | 중위소득 **140% 이하** | 판정 로직 변경 |
| **E8** | 취업패키지 서류 = 등본/졸업증명서/참여동의서 | 초본 + 통장사본 + 항목별 추가서류(면접확인서·영수증·응시확인서) | 전면 교체 |
| **E9** | 점수 계산 없음 | 심사표 100점 필요 | `stage3_scoring` 신설 또는 데모 측 보유 |
| **E10** | `DOCUMENT_TYPE_CONFUSION_GROUPS`에 등본/초본 | 유지하되 **필수는 초본** 방향으로 반전. `사업자등록증 ↔ 사업자등록증명` 쌍 추가 | 오분류 탐지 |
| **E11** | 제외대상 체크 미흡 | 8개 카테고리 (2.2절) | `conflicting_benefits` 확장 |
| **E12** | 취업패키지 보완 정책 | **7일 보완 가능** vs 두배적금 **보완 불가** | 사업별 분기 필요 |
| **E13** | `TARGET_REGIONS` (시군 집합만) | 시군별 **정원**까지 필요 (전주 550 … 진안 15) | 정원 데이터 추가, 커트라인 산정 |

> **협의 방식 제안**: `doc_type` 문자열 상수를 단일 소스로 두고(예: `engine/doc_types.py`) 데모·엔진·대시보드가 공유한다. 문자열 불일치가 가장 흔한 연동 사고 지점이다.

## 8. 수용 기준 (Definition of Done)

- [ ] 두배적금 신청을 **자필서명·종이 없이** 처음부터 끝까지 완주할 수 있다
- [ ] 발급 서류(초본·건보 3종·근로확인)만 파일 업로드이고, 나머지는 전부 웹 입력이다
- [ ] 업로드 후 **5초 이내** 적합/부적합/확인필요가 화면에 표시된다
- [ ] 근로유형을 바꾸면 요구 서류 목록이 **자동으로** 바뀐다
- [ ] 심사표 100점이 시행지침 서식6과 **수기 검산에서 일치**한다
- [ ] 담당자가 심사 1건을 처리하는 동안 파일 다운로드가 **0회**다
- [ ] 판정 근거를 클릭하면 원본 서류의 해당 위치가 하이라이트된다
- [ ] 신청자 화면 어디에도 심사 점수가 노출되지 않는다
- [ ] 10개 시연 시나리오가 리셋 후 재현된다
- [ ] 미확정 가정값(2.5절 등)이 화면과 코드에 라벨로 명시된다
- [ ] 신규 생성 파일이 **전부 `demo/` 하위**에 있다 — 루트·`engine/`·`dashboard/`에 추가·수정된 파일 없음 (`.gitignore`, `docs/` 제외)
- [ ] **서식1~5 화면이 PDF 원본과 항목 순서·각주 문구·체크 옵션 개수까지 일치한다**
- [ ] 담당자 심사표가 **서식6 원본 배점표 레이아웃**으로 보인다
- [ ] 자동 선택된 구간 체크박스 옆에 **근거 문장**이 붙어 있다
- [ ] 모바일(<1024px)에서 서식 항목 순서가 유지되고 가로 스크롤이 발생하지 않는다

**선택 항목 (P7 — 미구현이어도 DoD 충족)**

- [ ] 서식1·서식5를 작성된 상태 그대로 PDF로 내보낼 수 있다
- [ ] 서식5 PDF의 서명란에 전자서명이 합성되어 있다

## 10. TF 회의에서 확인해야 할 것

1. **중위소득 100/110/120/130% 구간별 건강보험료 기준표 원본** — 공고문에 140% 표만 있어 심사표 40점 항목 구간 판정이 불가능하다. 데모는 선형 환산 + `(데모 추정치)` 라벨로 진행 중.
2. **행정정보 공동이용 동의서(서식5)의 전자서명 대체 가능 여부** — 현행 지침 명문은 "자필서명(제3자가 알아볼 수 있도록) 후 첨부".
3. **공고문 "1개의 파일로 압축하여 올려야 함" 규정을 서류별 개별 업로드로 완화 가능한가** — 신청자가 직접 병합하는 과정이 누락·순서오류의 주요 원인이다.
4. **서식5의 공동이용 행정정보 코드 불일치** — 공고문 `371(주민등록표 A형)` vs 시행지침 `46(건강보험자격득실 A형) + 388(주민등록표 J형)`. 어느 쪽이 유효한가.
5. OCR 신뢰도가 낮을 때의 처리 절차 — 자동 반려인가, 담당자 큐인가. 임계값은 얼마인가.
6. 두배적금 "보완 요청 없음" 정책 유지 여부 (업로드 즉시 판정이 도입되면 완화 가능한가)
7. 담당자 심사 화면의 권한 분리 — 읍면동 / 시군(120%) / 도·청년허브센터(100%) 3단계를 데모에 반영할 것인가
8. 취업지원패키지 **선착순 판정 기준 시각** — 제출 시각인가, 서류 완비 시각인가
9. 부적합 판정 시 담당자에게 넘길 심사 요청 패키지의 확정 항목
10. 대시보드(채운)와의 화면 경계
