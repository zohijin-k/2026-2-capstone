# engine — 서류 적합성·자격 판단 엔진

담당: 진

전북청년 함께 두배적금 / 청년 취업지원 패키지의 제출 서류를 읽고,
신청자 입력값·다른 서류·사업 기준과 **교차검증**해서 적합 / 부적합 / 검토필요를 판정한다.

> 한 문장 정의: **담당자는 엔진이 판단하지 못한 예외만 본다. 기준이 바뀌어도 규칙팩만 바꾼다.**

---

## 0. 설계 원칙

| 원칙 | 의미 |
|---|---|
| 판정은 규칙이 한다 | LLM/모델은 "읽기"에만 쓴다. 적합/부적합 결정은 규칙팩이 결정적으로 내린다. 그래야 근거를 설명할 수 있다. |
| 기준은 코드 밖에 둔다 | 발급일 유효기간, 나이, 거주기간 등은 `rulepacks/*.yaml`에 둔다. 공고가 바뀌어도 코드는 안 바뀐다. |
| 출력은 두 갈래 | 신청자용(적합/부적합 + 보완 안내)과 담당자용(근거·신뢰도·배점)을 분리한다. **배점은 존재 자체가 대외비**이므로 신청자용 출력에 절대 포함하지 않는다. |
| 모르면 사람에게 | 신뢰도가 낮거나 판단 불가하면 억지로 판정하지 않고 `검토필요`로 보낸다. |
| 데이터는 밖으로 안 나간다 | 외부 API로 서류를 보내지 않는다. 판독은 로컬에서 한다. |
| 학습보다 평가 | 실제 서류 데이터는 학습용이 아니라 정확도 검증용으로만 쓴다. |

## 1. 범위와 가정 (1단계)

### 1-1. 범위

- **상세 구현 대상:** 주민등록표 **초본** (레퍼런스 구현. 다른 서류 엔진은 이 구조를 따른다)
- **인터페이스만 맞춤:** 면접확인서, 결제영수증(정장대여·사진관·자격증), 응시확인서, 성적표 — 담당: 채운·지빈
- **대상 사업:** 두배적금, 취업지원 패키지 두 개만
- **범위 밖:** 사후관리, 교육 매칭, 보고서 자동생성, 위변조 탐지

### 1-2. 데이터

- 실제 신청자 서류는 사용하지 않는다 (나루 측 데이터 제공 불가).
- 팀원 **본인 서류(PDF)** 를 양식 기준으로 사용한다. → `data/private/` 에만 두고 **절대 커밋하지 않는다.**
- 평가셋은 본인 서류 양식을 본뜬 **합성 서류**로 만든다 (적합 + 의도적 부적합 케이스).

### 1-3. 가정값 (허브센터/공고 확정 전 임시값)

> ⚠️ 표시는 TF 확정값으로 교체 필요. 모두 `rulepacks/`의 파라미터로 들어가며 코드에 하드코딩하지 않는다.

| ID | 항목 | 가정값 | 상태 |
|---|---|---|---|
| A1 | 초본 발급일 유효기간 | 공고일 기준 **30일 이내** 발급 | ⚠️ |
| A2 | 나이 기준일 | **공고일** 기준 만 나이 | ⚠️ |
| A3 | 나이 범위 | 만 **19~39세** | ⚠️ |
| A4 | 거주지 | 현주소가 전북특별자치도 14개 시군 | ⚠️ |
| A5 | 거주기간 | 공고일 기준 전북 내 **연속** 거주 **6개월 이상** (합산 아님) | ⚠️ |
| A6 | 입력값 일치 | 신청자가 입력한 성명·생년월일·발급일이 서류 값과 **정확히 일치** | ⚠️ |
| A7 | 서류 종류 | 등본이 아니라 **초본**이어야 함 (주소 변동 이력 필요) | 확인됨 (회의록) |
| A8 | 자동판정 임계값 | 필드 신뢰도 **0.90** 미만이면 검토필요 | 평가 후 조정 |

### 1-4. 설계 시 주의할 도메인 디테일

- **전라북도 → 전북특별자치도 (2024.1.18 명칭 변경).** 과거 주소 이력에는 "전라북도"로 찍혀 있으므로 거주기간 계산 시 두 표기를 같은 지역으로 매핑해야 한다.
- 전북 14개 시군: 전주, 군산, 익산, 정읍, 남원, 김제, 완주, 진안, 무주, 장수, 임실, 순창, 고창, 부안
- 초본은 주소 이력이 길면 여러 페이지로 나뉜다.
- 초본 발급 시 "주소 변동 사항 포함/미포함" 등 옵션에 따라 이력이 생략될 수 있다 → 이력 미포함 초본은 거주기간 판정 불가 → `검토필요` 또는 보완요청.

## 2. 입력·출력 계약 (2단계)

스키마 코드: [`schemas/`](schemas/)

### 2-1. 엔진 입력 — `ApplicationInput`

```
ApplicationInput
├── application_id        신청 고유번호
├── program_id            "doubling_savings" | "job_package"
├── announcement_date     공고일 (나이·발급일·거주기간 기준일)
├── applicant             신청자 입력값 (성명, 생년월일, 주소 등)  ← 엔진은 이 값을 믿지 않고 검증 대상으로 본다
└── documents[]
    ├── doc_id
    ├── declared_type     신청자가 "이게 초본이에요"라고 올린 칸
    ├── file_path
    └── declared_values   서류별로 신청자가 입력한 값 (예: 발급일)
```

### 2-2. 서류 단위 출력 — `DocumentResult`

```
DocumentResult
├── doc_id
├── declared_type / detected_type / type_confidence   ← 등본/초본 오분류 감지
├── fields{ name: ExtractedField }
│     ├── value          정규화된 값 (날짜는 ISO, 금액은 정수)
│     ├── raw_text       서류에 적힌 원문
│     ├── confidence     0~1
│     ├── source         text_layer | ocr | vlm
│     └── bbox           페이지 번호 + 좌표  ← 원본 위 근거 하이라이트용
├── checks[]: CheckResult
│     ├── rule_id / rule_type
│     ├── status         pass | fail | unknown
│     ├── applicant_message   신청자에게 보여줄 문구 (기준값 노출 X)
│     ├── reviewer_message    담당자용 상세 문구
│     └── evidence[]     어떤 필드 값으로 판단했는지
├── verdict              적합 | 부적합 | 검토필요
└── review_reasons[]     검토필요 사유
```

### 2-3. 신청 단위 출력 — `ApplicationResult`

```
ApplicationResult
├── application_id / program_id
├── documents[]           DocumentResult
├── missing_doc_types[]   필수인데 안 낸 서류
├── status                적합 | 부적합 | 검토필요
└── internal              ← 담당자 전용 (배점, 순위 산정용 값). 신청자용 변환 시 제거
```

### 2-4. 출력 분리

- `ApplicationResult.to_applicant_view()` → 신청자에게 보낼 결과만 남긴다
  - 남김: 서류별 판정, `applicant_message`, 누락 서류
  - 제거: `internal`(배점), 신뢰도, 기준 파라미터, 담당자용 메시지
- 담당자 화면은 `ApplicationResult` 전체를 쓴다

## 실측 기록

### 건강보험 서류 판독기 (가상 레이아웃 기준)

요청에 포함된 두 “가려진 칸 배치”가 비어 있어 실제 양식의 정확한 시각 배치는 확인하지 않았다.
추출기는 좌표를 고정하지 않고, 페이지 안의 라벨·열 제목을 찾은 뒤 같은 줄 오른쪽 또는
x 범위가 겹치는 아래쪽에서 값을 찾는다. 행 표는 페이지마다 열 제목을 다시 탐색한다.
실제 파일의 `--layout` 출력과 사용자 확인이 들어오기 전까지 아래는 구현상 가정이다.

- 납부확인서 라벨 후보: `성명`, `생년월일`, `주민등록번호`, `발급일`, `발급일자`, `발행일`,
  `출력일`, `직장가입자`/`지역가입자`, `년월`, `보험료월`, `납부월`, `납부년월`, `청구월`,
  `보험료연월`, `고지금액`, `고지보험료`, `납부금액`, `납부보험료`, `실납부`, `건강보험료`,
  `건강보험`, `장기요양보험료`, `장기요양`, `노인장기요양`, `합계`.
- 자격득실확인서 라벨 후보: `성명`, `생년월일`, `주민등록번호`, `발급일`, `발급일자`,
  `발행일`, `출력일`, `조회기간`, `대상기간`, `가입자구분`, `자격구분`, `자격취득일`,
  `취득일`, `자격상실일`, `상실일`, `사업장명칭`, `사업장명`, `사업장`.
- 라벨 문자열은 공백을 제거해 비교한다. 머리글에서 고지 열과 납부 열을 구별하지 못하거나
  건강보험료와 장기요양보험료 합계만 보이면 건강보험료 값을 만들지 않고 담당자 확인 경고를 낸다.
- 년월은 `2025.10`, `2025-10`, `2025년 10월`, `202510`, `2025. 10.` 표기를 지원한다.
  날짜는 `2025.10.01`, `2025-10-01`, `2025년 10월 1일`, `20251001`을 지원한다.
  금액에서 쉼표·공백·`원`을 제거해 정수로 읽으며, 0·음수는 확정하지 않는다.
- 열 머리글이 여러 줄이면 같은 x 범위를 공유하는 머리글 조각을 묶는다. 표는 페이지마다
  `년월` 등 열 제목을 다시 찾아 행을 나누며, 고지금액과 납부금액 열을 제목으로 구분할 수
  없을 때에는 값을 추측하지 않고 비운다. 표의 합계 줄이 있으면 월별 고지금액 합과 대조한다.
- `고지월`은 2025년 10·11·12월 중 실제 월 행을 찾은 결과이며, 건강보험료는 세 달의
  고지금액 평균을 가장 가까운 정수 원으로 반올림한다. 장기요양보험료 열이 별도로 식별되면
  같은 기간 평균을 독립 필드로 낸다. 공고문에서 장기요양보험료 처리 기준을 다시 확인해야 한다.
- 생년월일은 `생년월일` 라벨 옆 날짜를 우선 사용하고, 없으면 주민등록번호 앞 여섯 자리와
  성별 자리로 세기를 판별한다. 실제 서류의 머리글 표기와의 일치는 `--layout` 결과로 확인한다.
- 최근 5년 포함은 발급일 기준 5년 전부터 발급일까지 조회기간이 덮거나, 이 기간을 연속해
  덮는 가입 이력이 있을 때만 표시한다. 조회 기간도 이력 날짜도 확인되지 않으면 포함으로
  추정하지 않는다. 사업장명은 이력 파싱에만 쓰며 추출 필드, 경고, 출력에는 넣지 않는다.

### 2026-11-10 본인 초본 PDF 점검 (진)

| 항목 | 결과 |
|---|---|
| 생성 경로 | 크롬 "PDF로 저장" (`producer: Skia/PDF`, `creator: Chrome`) — 정부24 원본 파일 아님 |
| 페이지 | 3쪽 (A4) — 주소 이력이 길면 여러 쪽 |
| 텍스트 레이어 | **없음** (전 페이지 0자) |
| 이미지 | 페이지당 3~4개 — 배치 확인 필요 (`image_layout`) |

**설계 결정:** 신청자도 대부분 같은 방식(브라우저 인쇄 → PDF)으로 제출할 것이므로
**OCR을 주 경로**로 설계한다. 텍스트 레이어 추출은 있을 때만 쓰는 빠른 경로로 둔다.

**이미지 배치 (`image_layout`):**

| 이미지 | 위치 (pt) | 해상도 | 추정 역할 |
|---|---|---|---|
| ① 전체 덮음 99.9% | 0,0 ~ 595,842 | 250dpi | 본문 (모든 글자) |
| ② 하단 가로 띠 5.7% | 42,746 ~ 552,802 | 480dpi | 위변조방지 2차원 바코드 추정 |
| ③ 우상단 정사각형 | 494,20 ~ 544,70 (매 쪽) | 525dpi | QR·진위확인 마크 추정 |
| ④ 초소형 정사각형 | 535,61 ~ 553,79 (첫 쪽만) | 2400dpi | 보안 마크 추정 |

→ 배경무늬가 별도 레이어로 겹친 구조는 아님. 본문 이미지만 원본 해상도로 꺼내면
  바코드·마크가 자동으로 빠진 OCR 입력이 된다. (`pipeline/preprocess.py`)

**남은 확인:** 본문 이미지 안 배경무늬 → OCR 7/7로 영향 없음 확인.

## 3. 파이프라인 (3단계)

```
업로드 파일
  │
  ▼
① 전처리  pipeline/preprocess.py  ✅ 구현
  │   페이지별 경로 선택: text_layer → embedded(본문 이미지만 추출) → render(폴백)
  │   바코드 띠·모서리 마크는 OCR 입력에서 제외, 위치만 aux로 기록
  │   출력: PageImage[] (png, 픽셀 크기, dpi, 픽셀→pt 변환, 경고)
  ▼
② OCR      텍스트 + 단어별 픽셀 bbox + 신뢰도
  │   text_layer 페이지는 생략
  ▼
③ 분류     제목 키워드("주민등록표(초본)" / "(등본)") + 양식 특징으로 detected_type
  │   declared_type ≠ detected_type → 오분류 체크 실패
  ▼
④ 필드 추출 extractors/<서류>.py
  │   서류별 부품. 출력은 ExtractedField(value, raw_text, confidence, source, bbox)
  │   bbox는 PageImage.px_to_pt()로 pt 좌표 변환 → 원본 위 하이라이트
  ▼
⑤ 필드 검증 형식·범위 (날짜가 실제 날짜인지, 발급일이 미래가 아닌지 등)
  │   실패 시 해당 필드 confidence를 낮춤 → 이후 검토필요로 감
  ▼
⑥ 교차검증 rulepacks/<사업>.yaml 규칙 실행 → CheckResult[]
  ▼
⑦ 판정·라우팅
      필수 필드 저신뢰 / 판단불가(unknown) 있음 → 검토필요
      fail 하나라도 → 부적합 (신청자에게 보완 안내)
      전부 pass     → 적합
```

### 단계별 실패 처리

| 단계 | 실패 상황 | 처리 |
|---|---|---|
| ① | 암호 PDF, 지원 안 하는 형식 | 즉시 신청자에게 재업로드 안내 |
| ① | 해상도 200dpi 미만 | 경고 기록, OCR은 진행 |
| ② | 글자 거의 안 읽힘 | 검토필요 + "더 선명한 파일로" 안내 |
| ③ | 다른 서류 감지 | 부적합 ("초본을 올려주세요") |
| ④ | 필수 필드 못 찾음 | 해당 규칙 unknown → 검토필요 |
| ⑥ | 규칙 실패 | 부적합 + 규칙별 신청자 안내 문구 |

## 4. 규칙팩 (4단계)

파일: [`rulepacks/doubling_savings.yaml`](rulepacks/doubling_savings.yaml)

판정 기준은 전부 이 파일에 있다. 코드에는 "규칙 유형"만 구현하고, 어떤 값으로 판정할지는 규칙팩이 정한다.

### 규칙 유형 (코드로 구현할 것)

| 유형 | 하는 일 | 쓰는 곳 |
|---|---|---|
| `doc_type_is` | 감지된 서류 종류 확인 | 등본/초본 오분류 |
| `validation_passed` | 추출기 자체 검증 결과 사용 | 쪽 누락 |
| `equals_declared` | 서류 값 = 신청자가 그 서류에 입력한 값 | 발급일 입력 |
| `equals_applicant` | 서류 값 = 신청자 기본 정보 | 성명, 생년월일 |
| `date_within_days` | 기준일로부터 N일 이내 | 발급일 유효기간 |
| `age_between` | 기준일 만 나이 범위 | 연령 요건 |
| `current_sido_is` | 현 주소 시도 | 거주지 요건 |
| `residence_months_at_least` | 연속 거주 개월 수 | 거주기간 요건 |
| `date_order` | A ≤ B | 결제일 ≤ 면접일 (취업지원) |
| `amount_equals` | 금액 일치 | 청구액 = 영수증 (취업지원) |
| `date_in_range` | 기간 안 | 결제일이 모집기간 안 (취업지원) |
| `required_docs` | 필수 서류 조합 | 근로유형별 서류 |

### 규칙 하나의 구성

```yaml
- id: abstract.issue_date_recent        # 고유 ID (CheckResult.rule_id)
  type: date_within_days                # 위 유형 중 하나
  params: { field: issue_date, max_days: 30 }
  applicant: "최근에 새로 발급받은 초본을 올려주세요."   # 기준 수치 노출 금지
  reviewer: "발급일 {value}, {days}일 경과 (허용 {max_days}일)"
```

### 배점

`scoring:` 섹션에 둔다. 결과는 `ApplicationResult.internal`에만 들어가고,
신청자용 출력은 허용 필드만 내보내는 방식이라 구조적으로 섞일 수 없다. 배점표 확정 전까지 비워둔다.

## 5. 초본 상세 (5단계)

구현: [`extractors/resident_abstract.py`](extractors/resident_abstract.py) · 테스트: [`tests/test_resident_abstract.py`](tests/test_resident_abstract.py) (7개 통과)

### 실측 레이아웃 (페이지 대비 %)

| y | 내용 | 비고 |
|---|---|---|
| ≈3 | 문서확인번호 / 쪽번호 `n/N` (x≈79) | 매 쪽 |
| ≈7~10 | 제목 "주민등록표 ( 초 본 )" | 글자가 띄어져 읽힘 → 공백 제거 후 판별 |
| ≈12.8 | 발급일 `YYYY년 MM월 DD일` (x≈58) | 매 쪽 반복 |
| ≈14.5 | 발급기관 "○○시장" | |
| ≈17.7 | 성명 (x≈23) / 주민등록번호 (x≈68) | 매 쪽 반복 |
| 표 | 주소 x≈13 · 발생일 x≈54 · 신고일 x≈68 · 세대주 x≈79 · 사유 x≈62~73 | 한 건이 2줄 |
| ≈78~ | 안내 문구 | 무시 |

### 추출 필드

| 필드 | 방법 | 신뢰도 근거 |
|---|---|---|
| `issue_date` | 머리 영역 x>50의 `년월일` | 쪽 간 일치, 미래 아님, 문서확인번호 일치 |
| `name` | 주민등록번호 줄의 x 15~36 | 쪽 간 일치, 한글 2~6자 |
| `birth_date` | 주민번호 앞 6자리 + 성별자리로 세기 판정 | 쪽 간 일치 |
| `address_history` | 표 영역, **신고일 칸이 있는 줄 = 새 건** | 순번 연속, 날짜 순서, 발생일 ≤ 신고일 |
| `current_address` | 마지막 건 | 위 + 시도 판별 성공 |

### 처리한 함정

- **순번 위치가 들쭉날쭉:** 윗줄/아랫줄 어디든 올 수 있음 → 줄이 아니라 신고일 칸으로 건을 나눔
- **주소가 두 줄:** 아랫줄 x≈13 텍스트를 앞 건 주소에 이어 붙임
- **`[...]` 메모 줄:** 도로명주소 전환·행정구역 변경 안내 → 건으로 세지 않고 다음 건에 메모로 붙임. **단, 메모 줄도 자기 순번을 가지므로 순번 연속 검사에는 포함** (실측에서 발견)
- **전라북도 → 전북특별자치도:** 둘 다 `전북`으로 매핑. 명칭 변경 건이 거주기간을 끊지 않음 (테스트로 확인)
- **시도가 안 적힌 건:** 앞 건의 시도를 이어받음
- **서버 시간대:** 판정 기준일은 항상 한국 시간 (UTC면 오전 9시 전 당일 발급분이 '미래'로 오판)

### 개인정보 최소화

- 주민등록번호는 생년월일과 성별 자리만 쓰고 원문은 결과에 남기지 않음 (`YYMMDD-G******`)
- 병역사항, 담당자 연락처, 신청인 정보는 읽지 않음

## 6. 신뢰도·라우팅 (6단계)

### 필드 신뢰도 = 검증 통과율

```
confidence = 0.4 + 0.6 × (통과한 검증 수 / 전체 검증 수)
치명적 실패(예: 발급일이 미래) → 0.2
```

OCR 엔진 점수는 쓰지 않는다 (실측: 정답 7/7인데 단어 43%가 0.8 미만).

쪽마다 값이 다르게 읽힌 필드는 **신뢰도 상한 0.6** (오독 신호 → 자동 부적합에 쓰지 않음).

### 판정

| 조건 | 판정 | 누가 보나 |
|---|---|---|
| 서류 종류 불일치 | 부적합 | 신청자 (즉시 재업로드 안내) |
| 규칙 하나라도 fail, 관련 필드 신뢰도 ≥ 0.7 | 부적합 | 신청자 |
| 규칙 fail인데 관련 필드 신뢰도 < 0.7 | **검토필요** | 담당자 (오독일 수 있음) |
| 필수 필드 없음 / 규칙 unknown | **검토필요** | 담당자 |
| 전부 pass | 적합 | — |

신뢰도 0.7은 임시값. 평가셋으로 "부적합을 놓치지 않으면서 검토필요를 최소화하는 값"을 찾아 조정한다.

## 7. OCR 엔진 선택 (7단계)

OCR이 주 경로가 되었으므로 7단계를 먼저 한다. 어댑터: `pipeline/ocr.py`, 비교 도구: `tools/ocr_bench.py`

| 후보 | 설치 | 서버(리눅스) 배포 | 역할 |
|---|---|---|---|
| Apple Vision (`ocrmac`) | `pip install ocrmac` | 불가 (맥 전용) | 기준선 |
| EasyOCR | `pip install easyocr` | 가능 | 후보 |
| PaddleOCR | `pip install paddlepaddle paddleocr` | 가능 | 후보 |

비교 지표: 쪽당 처리시간, 평균 신뢰도, 저신뢰 비율, 고정 문구 적중, **정답 필드 적중**(본인 PC의 정답 파일 기준)

선정 기준: 정답 필드 적중 최우선 → 쪽당 처리시간 → 서버 배포 가능 여부

| 날짜 | 엔진 | 쪽당 시간 | 평균 신뢰도 | 저신뢰(<0.8) | 키워드 | 정답 필드 | 비고 |
|---|---|---|---|---|---|---|---|
| 11-10 | Apple Vision | 1.5초 | 0.782 | 43% | 15/17 | **7/7** | 본인 초본 3쪽. 키워드 2개 미적중은 시장/군수/구청장 중 하나만 존재하므로 정상 |

### 발견: OCR 신뢰도 ≠ 정답 여부

정답 7/7인데 단어의 43%가 신뢰도 0.8 미만. **엔진이 내는 신뢰도는 라우팅 기준으로 쓸 수 없다.**

→ 가정 A8 폐기. 필드 신뢰도는 **검증 통과 여부로 산정**한다:

| 검증 | 예 | 통과 시 |
|---|---|---|
| 형식 | 실제 존재하는 날짜인가, 발급일이 미래가 아닌가 | + |
| 서류 내부 일관성 | 생년월일 ↔ 주민번호 앞자리, 같은 값의 반복 등장 | ++ |
| 입력값 일치 | 신청자 입력 생년월일·발급일과 일치 | ++ |

OCR 신뢰도는 동점일 때 보조 지표로만 쓴다. 상세 산정식은 6단계에서 정한다.
