# engine — 서류 적합성·자격 판단 엔진

전북청년 함께 두배적금 / 청년 취업지원 패키지의 제출 서류를 읽고,
신청자 입력값·다른 서류·사업 기준과 **교차검증**해서 적합 / 부적합 / 검토필요를 판정한다.

> 한 문장 정의: **담당자는 엔진이 판단하지 못한 예외만 본다. 기준이 바뀌어도 규칙팩만 바꾼다.**

---

## 0. 설계 원칙

| 원칙 | 의미 |
|---|---|
| 판정은 규칙이 한다 | LLM/모델은 "읽기"에만 쓴다. 적합/부적합 결정은 규칙팩이 결정적으로 내린다. 그래야 근거를 설명할 수 있다. |
| 기준은 코드 밖에 둔다 | 발급일 유효기간, 나이, 거주기간 등은 `rulepacks/*.yaml`에 둔다. 공고가 바뀌어도 코드는 안 바뀐다. |
| 출력은 두 갈래 | 신청자용(적합/부적합 + 보완 안내)과 담당자용(근거·신뢰도·배점)을 분리한다. **배점은 존재 자체가 대외비**이므로 신청자용 출력에 절대 포함하지 않는다. |
| 모르면 사람에게 | 신뢰도가 낮거나 판단 불가하면 억지로 판정하지 않고 `검토필요`로 보낸다. |
| 실서류 전송은 제한한다 | 승인되지 않은 외부 API로 실제 서류를 보내지 않는다. 전북AI는 명시적 설정과 기관 확인 범위 안에서만 연결한다. |
| 학습보다 평가 | 실제 서류 데이터는 학습용이 아니라 정확도 검증용으로만 쓴다. |

## 1. 범위와 가정 (1단계)

### 1-1. 범위

- **상세 구현 대상:** 주민등록표 **초본** (레퍼런스 구현. 다른 서류 엔진은 이 구조를 따른다)
- **라벨 기반 판독기(뼈대):** 결제영수증(정장대여·사진관·자격증), 응시확인서·성적표, 면접확인서 — 아래 '취업지원패키지 추가서류' 절
- **대상 사업:** 두배적금, 취업지원 패키지 두 개만
- **범위 밖:** 사후관리, 교육 매칭, 보고서 자동생성, 위변조 탐지

### 1-2. 데이터

- 실제 신청자 서류는 사용하지 않는다 (나루 측 데이터 제공 불가).
- 팀원 **본인 서류(PDF)** 를 양식 기준으로 사용한다. → `data/private/` 에만 두고 **절대 커밋하지 않는다.**
- 평가셋은 본인 서류 양식을 본뜬 **합성 서류**로 만든다 (적합 + 의도적 부적합 케이스).

### 1-3. 가정값 (허브센터/공고 확정 전 임시값)

> ⚠️ 표시는 TF 확정값으로 교체 필요. 모두 `rulepacks/`의 파라미터로 들어가며 코드에 하드코딩하지 않는다.

| ID | 항목 | 가정값 | 상태 |
|---|---|---|---|
| A1 | 서류 발급일 기준 | 데모 DB의 신청서별 적용 기준 버전에서 읽음 (`after_date` / `after_notice` / `within_days` / `none`) | 설정값 |
| A2 | 나이 기준일 | **공고일** 기준 만 나이 | ⚠️ |
| A3 | 나이 범위 | 만 **19\~39세** | ⚠️ |
| A4 | 거주지 | 현주소가 전북특별자치도 14개 시군 | ⚠️ |
| A5 | 거주기간 | 공고일 기준 전북 내 **연속** 거주 **6개월 이상** (합산 아님) | ⚠️ |
| A6 | 입력값 일치 | 신청자가 입력한 성명·생년월일·발급일이 서류 값과 **정확히 일치** | ⚠️ |
| A7 | 서류 종류 | 등본이 아니라 **초본**이어야 함 (주소 변동 이력 필요) | 확인됨 (회의록) |
| A8 | 자동판정 임계값 | 필드 신뢰도 **0.90** 미만이면 검토필요 | 평가 후 조정 |

`doubling_savings.yaml`에는 초본 30일 규칙을 두지 않는다. 데모는 `Application.criteria_version`으로
신청서가 생성될 때의 기준 이력을 고정하고, 발급일 방식과 날짜는 해당 버전에서 가져온다.
규칙팩의 `settings_issue_date`는 이 값을 사용하는 연결점이다.

### 1-4. 데모 심사 기준 설정

사업별 기준 이력은 `demo/backend`의 `ProgramCriteriaVersion`에 저장한다. 기본 설정은 현재
프로그램 값에서 최초 생성하며, 변경 시 이전 이력을 유지한 채 버전을 하나 추가한다.
신청서는 생성 당시 버전 번호를 보관한다. 납부확인서의 평균 대상 고지월 기본값은
2025-10, 2025-11, 2025-12이고, 자격득실확인서 포함 기간 기본값은 5년이다.

건강보험료 납부확인서의 `보수외소득월액_건강`은 별도 판독값이다. 건강보험료 평균에
합산할지는 공고문 기준 확인이 필요하다. 장기요양보험료도 독립 항목으로 두며 합산하지 않는다.
현재 정부24 서식의 직장가입자 배치를 바탕으로 구현했다. 지역가입자 서류에서 가입구분을
얻는 위치와 해당 서식의 표 머리글 구조는 실제 배치를 확인하지 못해 미확정이다.

### 1-5. 설계 시 주의할 도메인 디테일

- **전라북도 → 전북특별자치도 (2024.1.18 명칭 변경).** 과거 주소 이력에는 "전라북도"로 찍혀 있으므로 거주기간 계산 시 두 표기를 같은 지역으로 매핑해야 한다.
- 전북 14개 시군: 전주, 군산, 익산, 정읍, 남원, 김제, 완주, 진안, 무주, 장수, 임실, 순창, 고창, 부안
- 초본은 주소 이력이 길면 여러 페이지로 나뉜다.
- 초본 발급 시 "주소 변동 사항 포함/미포함" 등 옵션에 따라 이력이 생략될 수 있다 → 이력 미포함 초본은 거주기간 판정 불가 → `검토필요` 또는 보완요청.

## 2. 입력·출력 계약 (2단계)

스키마 코드: [`schemas/`](schemas/)

### 2-1. 엔진 입력 — `ApplicationInput`

```
ApplicationInput
├── application_id        신청 고유번호
├── program_id            "doubling_savings" | "job_package"
├── announcement_date     공고일 (나이·발급일·거주기간 기준일)
├── applicant             신청자 입력값 (성명, 생년월일, 주소 등)  ← 엔진은 이 값을 믿지 않고 검증 대상으로 본다
└── documents[]
    ├── doc_id
    ├── declared_type     신청자가 "이게 초본이에요"라고 올린 칸
    ├── file_path
    └── declared_values   서류별로 신청자가 입력한 값 (예: 발급일)
```

### 2-2. 서류 단위 출력 — `DocumentResult`

```
DocumentResult
├── doc_id
├── declared_type / detected_type / type_confidence   ← 등본/초본 오분류 감지
├── fields{ name: ExtractedField }
│     ├── value          정규화된 값 (날짜는 ISO, 금액은 정수)
│     ├── raw_text       서류에 적힌 원문
│     ├── confidence     0\~1
│     ├── source         text_layer | ocr | vlm
│     └── bbox           페이지 번호 + 좌표  ← 원본 위 근거 하이라이트용
├── checks[]: CheckResult
│     ├── rule_id / rule_type
│     ├── status         pass | fail | unknown
│     ├── applicant_message   신청자에게 보여줄 문구 (기준값 노출 X)
│     ├── reviewer_message    담당자용 상세 문구
│     └── evidence[]     어떤 필드 값으로 판단했는지
├── verdict              적합 | 부적합 | 검토필요
└── review_reasons[]     검토필요 사유
```

### 2-3. 신청 단위 출력 — `ApplicationResult`

```
ApplicationResult
├── application_id / program_id
├── documents[]           DocumentResult
├── missing_doc_types[]   필수인데 안 낸 서류
├── status                적합 | 부적합 | 검토필요
└── internal              ← 담당자 전용 (배점, 순위 산정용 값). 신청자용 변환 시 제거
```

### 2-4. 출력 분리

- `ApplicationResult.to_applicant_view()` → 신청자에게 보낼 결과만 남긴다
  - 남김: 서류별 판정, `applicant_message`, 누락 서류
  - 제거: `internal`(배점), 신뢰도, 기준 파라미터, 담당자용 메시지
- 담당자 화면은 `ApplicationResult` 전체를 쓴다

## 4대 사회보험 가입내역 확인서

확인한 서식은 한 쪽이며, 제목은 `4대 사회보험` / `가입자 가입내역 확인서` 두 줄이다.
표의 열은 보험 구분, 성명, 가입자종별, 사업장 관리번호, 사업장명칭, 자격취득일(신고접수일) 순서다.
보험 행은 국민연금·건강보험·산재보험·고용보험 순서이며 마지막 열에서 자격취득일 아래
괄호 날짜는 신고접수일이다. 빈 신고접수일은 `(-)`로 표시된다. 실제 가린 layout_dump에서는
표 머리글 두 줄, 보험별 네 행, 미가입 표기와 마지막 열의 날짜/괄호 날짜가 확인됐다. 미가입 행의 반복 `미가입`은
상태로 정규화하고 대시는 빈 값으로 둔다. 이 서류는 발급일 현재 내역만 표시하므로 상실일과
과거 이력은 읽지 않는다. 여러 사업장이면 별도 서류로 발급될 수 있다.

판독 결과에는 보험별 행과 보험별 가입 여부·가입자종별, 근로 관련 가입 여부 및 관련 행의
최초·최근 자격취득일, 사업장명칭 목록이 있다. 이는 추출 요약이며 공고일과 비교하는 근로
요건 판정은 포함하지 않는다. 주민등록번호 뒤 6자리는 생년월일 계산 뒤 버린다.

## 취업지원패키지 추가서류

결제영수증(`extractors/receipt.py`)·응시확인서/성적표(`exam_docs.py`)·면접확인서(`interview_confirmation.py`)는
모양이 하나로 정해져 있지 않아 좌표 대신 '라벨 → 값'으로 읽는다(공통 처리 `job_common.py`, 건강보험의
`nhis_common`과 같은 역할). 필드 이름은 데모 규칙이 쓰는 한국어 이름이고 금액은 `nhis_payment`·make_gt와 같이
숫자 문자열이다. 접수확인서·수험표는 해당 서류로 판별하지 않는다. 판정은 하지 않으며 서류별 규칙은
`rulepacks/job_package.yaml`(초안)이 본다.

팀 평가 도구에 그대로 붙어 있다: 합성 세트 `make_synth_eval --suite job_package` → `ocr_bench --synth`,
실서류 `ocr_bench <파일> --gt <정답> --doc receipt`(값 미출력), 진단 `extract_diag <파일> --doc receipt`.
결함 서류 시나리오는 `make_job_docs` → `job_docs_bench`. 기본 합성 세트와 진단 재현 사례는 바뀌지 않는다.
필드·검증 목록, 측정 결과와 한계는 [`docs/job-docs.md`](docs/job-docs.md)를 참고한다.

## 실측 기록

### 건강보험 서류 판독기 (가상 레이아웃 기준)

요청에 포함된 두 “가려진 칸 배치”가 비어 있어 실제 양식의 정확한 시각 배치는 확인하지 않았다.
추출기는 좌표를 고정하지 않고, 페이지 안의 라벨·열 제목을 찾은 뒤 같은 줄 오른쪽 또는
x 범위가 겹치는 아래쪽에서 값을 찾는다. 행 표는 페이지마다 열 제목을 다시 탐색한다.
실제 파일의 `--layout` 출력과 사용자 확인이 들어오기 전까지 아래는 구현상 가정이다.

- 납부확인서 라벨 후보: `성명`, `생년월일`, `주민등록번호`, `발급일`, `발급일자`, `발행일`,
  `출력일`, `직장가입자`/`지역가입자`, `년월`, `보험료월`, `납부월`, `납부년월`, `청구월`,
  `보험료연월`, `고지금액`, `고지보험료`, `납부금액`, `납부보험료`, `실납부`, `건강보험료`,
  `건강보험`, `장기요양보험료`, `장기요양`, `노인장기요양`, `합계`.
- 자격득실확인서 라벨 후보: `성명`, `생년월일`, `주민등록번호`, `발급일`, `발급일자`,
  `발행일`, `출력일`, `조회기간`, `대상기간`, `가입자구분`, `자격구분`, `자격취득일`,
  `취득일`, `자격상실일`, `상실일`, `사업장명칭`, `사업장명`, `사업장`.
- 라벨 문자열은 공백을 제거해 비교한다. 머리글에서 고지 열과 납부 열을 구별하지 못하거나
  건강보험료와 장기요양보험료 합계만 보이면 건강보험료 값을 만들지 않고 담당자 확인 경고를 낸다.
- 년월은 `2025.10`, `2025-10`, `2025년 10월`, `202510`, `2025. 10.` 표기를 지원한다.
  날짜는 `2025.10.01`, `2025-10-01`, `2025년 10월 1일`, `20251001`을 지원한다.
  금액에서 쉼표·공백·`원`을 제거해 부호가 있는 정수로 읽는다. 0은 정상값이며 음수는
  값으로 보존하고 정산·환급 확인 경고를 낸다.
- 열 머리글이 여러 줄이면 같은 x 범위를 공유하는 머리글 조각을 묶는다. 표는 페이지마다
  `년월` 등 열 제목을 다시 찾아 행을 나누며, 고지금액과 납부금액 열을 제목으로 구분할 수
  없을 때에는 값을 추측하지 않고 비운다. 표의 합계 줄이 있으면 월별 고지금액 합과 대조한다.
- `월별고지금액`과 `월별장기요양보험료`에는 판독한 월별 값 전체를 보존한다. 평균 대상 월은
  신청서에 저장된 심사 기준 버전이 정하며, 데모의 초기값은 2025년 10·11·12월이다.
  합산 여부를 회의에서 확정할 때까지 `보수외소득월액_건강`은 별도 값으로 두며 건강보험료
  평균에 합치지 않는다. 장기요양보험료도 별도 값이다.
- 생년월일은 `생년월일` 라벨 옆 날짜를 우선 사용하고, 없으면 주민등록번호 앞 여섯 자리와
  성별 자리로 세기를 판별한다. 실제 서류의 머리글 표기와의 일치는 `--layout` 결과로 확인한다.
- 자격득실확인서의 포함 기간은 신청서의 적용 기준 버전에서 읽는다(초기값 5년). 발급일
  기준 N년 전부터 발급일까지 조회기간이 덮거나, 이 기간을 연속해
  덮는 가입 이력이 있을 때만 표시한다. 조회 기간도 이력 날짜도 확인되지 않으면 포함으로
  추정하지 않는다. 사업장명은 이력 파싱에만 쓰며 추출 필드, 경고, 출력에는 넣지 않는다.

### 초본 판독 점검 (개인정보·서식 값 미기록)

실제 초본은 텍스트 레이어가 없는 이미지 PDF여서 OCR 경로로 처리한다. 전북AI 시험에서는
서류별 필수 항목·쪽 완전성 검증을 통과하지 못해 로컬 OCR로 대체됐다. 로컬 OCR 경로는
판독 검증을 통과했다. 실서류 판독 결과의 값과 수치는 이 문서에 기록하지 않는다.

실제 서류와 별도로, 가상 값으로 만든 합성 자료와 가짜 OCR 결과를 사용해 추출기·규칙
연결을 시험한다. 좌표·라벨 처리와 OCR 신뢰도만으로 정답 여부를 단정하지 않는 설계는
이 재생 가능한 시험 자료를 기준으로 확인한다.

### 엔진 전체 실행 기록

초본 입력은 전처리 → OCR → 추출 → 내부 검증 → 규칙 판정 흐름을 거친다. 합성 시나리오에서
정상 입력은 적합으로, 입력 발급일과 서류 발급일이 다른 경우에는 해당 불일치 안내로
처리되는 것을 확인한다. 기준값·거주기간·신뢰도와 배점은 신청자 응답에 포함하지 않는다.

## 3. 파이프라인 (3단계)

```
업로드 파일
  │
  ▼
① 전처리  pipeline/preprocess.py  ✅ 구현
  │   페이지별 경로 선택: text_layer → embedded(본문 이미지만 추출) → render(폴백)
  │   바코드 띠·모서리 마크는 OCR 입력에서 제외, 위치만 aux로 기록
  │   출력: PageImage[] (png, 픽셀 크기, dpi, 픽셀→pt 변환, 경고)
  ▼
② OCR      텍스트 + 단어별 픽셀 bbox + 신뢰도
  │   text_layer 페이지는 생략
  ▼
③ 분류     제목 키워드("주민등록표(초본)" / "(등본)") + 양식 특징으로 detected_type
  │   declared_type ≠ detected_type → 오분류 체크 실패
  ▼
④ 필드 추출 extractors/<서류>.py
  │   서류별 부품. 출력은 ExtractedField(value, raw_text, confidence, source, bbox)
  │   bbox는 PageImage.px_to_pt()로 pt 좌표 변환 → 원본 위 하이라이트
  ▼
⑤ 필드 검증 형식·범위 (날짜가 실제 날짜인지, 발급일이 미래가 아닌지 등)
  │   실패 시 해당 필드 confidence를 낮춤 → 이후 검토필요로 감
  ▼
⑥ 교차검증 rulepacks/<사업>.yaml 규칙 실행 → CheckResult[]
  ▼
⑦ 판정·라우팅
      필수 필드 저신뢰 / 판단불가(unknown) 있음 → 검토필요
      fail 하나라도 → 부적합 (신청자에게 보완 안내)
      전부 pass     → 적합
```

### 단계별 실패 처리

| 단계 | 실패 상황 | 처리 |
|---|---|---|
| ① | 암호 PDF, 지원 안 하는 형식 | 즉시 신청자에게 재업로드 안내 |
| ① | 해상도 200dpi 미만 | 경고 기록, OCR은 진행 |
| ② | 글자 거의 안 읽힘 | 검토필요 + "더 선명한 파일로" 안내 |
| ③ | 다른 서류 감지 | 부적합 ("초본을 올려주세요") |
| ④ | 필수 필드 못 찾음 | 해당 규칙 unknown → 검토필요 |
| ⑥ | 규칙 실패 | 부적합 + 규칙별 신청자 안내 문구 |

## 4. 규칙팩 (4단계)

파일: [`rulepacks/doubling_savings.yaml`](rulepacks/doubling_savings.yaml)

판정 기준은 전부 이 파일에 있다. 코드에는 "규칙 유형"만 구현하고, 어떤 값으로 판정할지는 규칙팩이 정한다.

### 규칙 유형 (코드로 구현할 것)

| 유형 | 하는 일 | 쓰는 곳 |
|---|---|---|
| `doc_type_is` | 감지된 서류 종류 확인 | 등본/초본 오분류 |
| `validation_passed` | 추출기 자체 검증 결과 사용 | 쪽 누락 |
| `equals_declared` | 서류 값 = 신청자가 그 서류에 입력한 값 | 발급일 입력 |
| `equals_applicant` | 서류 값 = 신청자 기본 정보 | 성명, 생년월일 |
| `date_within_days` | 기준일로부터 N일 이내 | 발급일 유효기간 |
| `settings_issue_date` | 신청서 적용 기준의 발급일 방식 | 사업별 발급일 인정 기준 |
| `age_between` | 기준일 만 나이 범위 | 연령 요건 |
| `current_sido_is` | 현 주소 시도 | 거주지 요건 |
| `residence_months_at_least` | 연속 거주 개월 수 | 거주기간 요건 |
| `date_order` | A ≤ B | 결제일 ≤ 면접일 (취업지원) |
| `amount_equals` | 금액 일치 | 청구액 = 영수증 (취업지원) |
| `date_in_range` | 기간 안 | 결제일이 모집기간 안 (취업지원) |
| `required_docs` | 필수 서류 조합 | 근로유형별 서류 |

### 규칙 하나의 구성

```yaml
- id: abstract.issue_date_recent        # 고유 ID (CheckResult.rule_id)
  type: settings_issue_date             # 적용 기준 버전에서 발급일 규칙을 읽음
  params: { field: issue_date }
  applicant: "사업에 설정된 발급일 기준에 맞는 초본을 올려주세요."
  reviewer: "발급일 {value} · 설정 기준 {cutoff} · 방식 {mode}"
```

### 배점

`scoring:` 섹션에 둔다. 결과는 `ApplicationResult.internal`에만 들어가고,
신청자용 출력은 허용 필드만 내보내는 방식이라 구조적으로 섞일 수 없다. 배점표 확정 전까지 비워둔다.

## 5. 초본 상세 (5단계)

구현: [`extractors/resident_abstract.py`](extractors/resident_abstract.py) · 테스트: [`tests/test_resident_abstract.py`](tests/test_resident_abstract.py) (7개 통과)

### 초본 레이아웃 구조

실서류의 개인별 값과 좌표는 공개 문서에 기록하지 않는다. 추출기는 페이지에 인쇄된 라벨을
기준으로 머리글과 주소 이력 표를 구분한다.

| 영역 | 내용 | 처리 |
|---|---|---|
| 머리글 | 문서확인번호, 쪽 번호, 서류 제목, 발급일 | 페이지 간 일치 검증 |
| 신청인 정보 | 성명, 생년월일, 주민등록번호 앞부분 | 식별에 필요한 값만 추출 |
| 주소 이력 표 | 주소, 발생일, 신고일, 세대주 관계, 변동 사유 | 신고일을 기준으로 이력 행 구분 |
| 안내 영역 | 서류 하단 안내·진위 확인 요소 | 이력 판독에서 제외 |

### 추출 필드

| 필드 | 방법 | 신뢰도 근거 |
|---|---|---|
| `issue_date` | 머리 영역 x>50의 `년월일` | 쪽 간 일치, 미래 아님, 문서확인번호 일치 |
| `name` | 주민등록번호 줄의 x 15\~36 | 쪽 간 일치, 한글 2\~6자 |
| `birth_date` | 주민번호 앞 6자리 + 성별자리로 세기 판정 | 쪽 간 일치 |
| `address_history` | 표 영역, **신고일 칸이 있는 줄 = 새 건** | 순번 연속, 날짜 순서, 발생일 ≤ 신고일 |
| `current_address` | 마지막 건 | 위 + 시도 판별 성공 |

### 처리한 함정

- **순번 위치가 들쭉날쭉:** 윗줄/아랫줄 어디든 올 수 있음 → 줄이 아니라 신고일 칸으로 건을 나눔
- **주소가 두 줄:** 아랫줄 x≈13 텍스트를 앞 건 주소에 이어 붙임
- **`[...]` 메모 줄:** 주소 표기나 행정구역 변경 안내 → 건으로 세지 않고 다음 건에 메모로 붙임. 메모 줄 순번은 행 연속성 검증에 포함한다.
- **전라북도 → 전북특별자치도:** 둘 다 `전북`으로 매핑. 명칭 변경 건이 거주기간을 끊지 않음 (테스트로 확인)
- **시도가 안 적힌 건:** 앞 건의 시도를 이어받음
- **서버 시간대:** 판정 기준일은 항상 한국 시간 (UTC면 오전 9시 전 당일 발급분이 '미래'로 오판)

### 개인정보 최소화

- 주민등록번호는 생년월일과 성별 자리만 쓰고 원문은 결과에 남기지 않음 (`YYMMDD-G******`)
- 병역사항, 담당자 연락처, 신청인 정보는 읽지 않음

## 6. 신뢰도·라우팅 (6단계)

### 필드 신뢰도 = 검증 통과율

```
confidence = 0.4 + 0.6 × (통과한 검증 수 / 전체 검증 수)
치명적 실패(예: 발급일이 미래) → 0.2
```

OCR 엔진 점수만으로 정답 여부를 정하지 않는다. 실측에서 글자 인식 점수와 필드 정답 여부가 항상 일치하지 않는 사례를 확인했다.

쪽마다 값이 다르게 읽힌 필드는 **신뢰도 상한 0.6** (오독 신호 → 자동 부적합에 쓰지 않음).

### 판정

| 조건 | 판정 | 누가 보나 |
|---|---|---|
| 서류 종류 불일치 | 부적합 | 신청자 (즉시 재업로드 안내) |
| 규칙 하나라도 fail, 관련 필드 신뢰도 ≥ 0.7 | 부적합 | 신청자 |
| 규칙 fail인데 관련 필드 신뢰도 < 0.7 | **검토필요** | 담당자 (오독일 수 있음) |
| 필수 필드 없음 / 규칙 unknown | **검토필요** | 담당자 |
| 전부 pass | 적합 | — |

신뢰도 0.7은 임시값. 평가셋으로 "부적합을 놓치지 않으면서 검토필요를 최소화하는 값"을 찾아 조정한다.

## 7. OCR 엔진 선택과 실행

공통 어댑터는 `pipeline/ocr/`에 있고 `own.py` 등 엔진별 모듈이 `OcrWord(text, confidence, bbox_px)`를 반환한다. 엔진 비교 도구는 `tools/ocr_bench.py`다. 자체 엔진 설치·모델 출처·평가 범위는 [`docs/own-ocr.md`](docs/own-ocr.md)를 참고한다.

`engine_v2.engine.run`과 CLI는 `ENGINE_V2_OCR`로 다음 엔진을 선택한다. 지정하지 않으면 macOS에서는 Apple Vision, 그 밖의 환경에서는 `own`을 사용한다.

| 값 | 설치 | 서버(리눅스) 배포 | 역할 |
|---|---|---|---|
| `applevision` | `ocrmac` 의존성 | 불가 (macOS 전용) | macOS 기본값 |
| `own` | PP-OCRv5 mobile 검출·한국어 인식 ONNX 변환본, ONNX Runtime CPU; 모델 출처 Apache-2.0 | 가능 | macOS 외 기본값; `python engine_v2/tools/fetch_own_models.py`로 모델 설치 |
| `easyocr` | EasyOCR 선택 의존성 | 가능 | 비교용 로컬 엔진 |
| `paddle` | PaddleOCR 선택 의존성 | 가능 | 비교용 로컬 엔진 |
| `off` | 없음 | 가능 | OCR을 사용하지 않음 |

전북AI OpenAI 호환 OCR은 `pipeline/jbai_ocr.py`의 쪽별 텍스트·표 결과로 받는다.
기존 `OcrWord`와 달리 bbox가 없고, 표 응답은 HTML 또는 OTSL 토큰이다. `extractors/jbai_text.py`가
기존 초본·납부확인서·자격득실 추출기의 결과 계약에 맞춰 연결되며, `run(..., ocr_engine="jbai")`로
선택할 수 있다. `jbai`는 `ENGINE_V2_OCR` 선택값이 아닌 별도 명시 엔진 인자다. 데모는 기관 확인에 따라 `demo/backend/ocr/jbai.py`에서 전북AI를 기본 판독으로 쓰고,
통신 오류 또는 서류별 필수 항목·판독 검증 실패 시 로컬 OCR로 대체한다. 검증이 통과하면
환각 점수와 무관하게 전북AI 결과를 사용하고, 잡음 여부는 담당자 화면에 참고 표시한다.
요청은 `temperature=0`, 기본 `max_tokens=4096`을 사용한다. 토큰 한도는 선택 환경변수
`JBAI_MAX_TOKENS`로 바꿀 수 있으며, 서버가 요청 옵션을 HTTP 400으로 거부하면 해당 옵션을
빼고 재요청한다. 모델 특수 토큰은 판독 텍스트에 남기지 않는다. `python -m engine_v2.tools.ocr_bench <합성.pdf> --engines jbai-ocr jbai-table`에서 합성 자료로 엔진을 비교할 수 있고,
인식 값은 콘솔이나 파일에 출력하지 않는다. 키는 `JBAI_API_KEY` 환경변수에서만 읽고,
`JBAI_ALLOW_REAL_DOCS`가 true가 아니면 `data/private/` 파일과 데모 업로드는 차단한다.

전북AI OCR은 JPG만 받으므로 전송 이미지는 JPEG다. PDF는 쪽마다 200dpi RGB(알파 없음)로 렌더링해
품질 95 JPEG로 만들고(`render_pdf_pages_200dpi`), 사진은 EXIF 회전을 반영한 RGB JPEG로 바꾼다
(`image_file_to_jpeg`, `run_jbai_file_pair`). 32MB 제한은 실제 전송하는 JPEG 바이트로 검사한다.
응답 원문의 주민등록번호는 받은 즉시 `mask_rrn`으로 성별 자리 뒤 6자리를 지우고, 모델 특수 토큰을
제거한 텍스트만 `text_lines`·`tables`·`raw_content`에 남긴다(추출기는 생년월일과 성별 자리만 쓴다).
쪽별 비한국어 문자 비율·반복 줄·이미지 대비 응답 길이를 합산해 잡음 점수를 계산한다.
이 점수만으로 로컬 OCR로 대체하지는 않는다. 필수 항목이나 서류 내부 검증이 실패할 때
대체하며, 그때 잡음 기준도 넘은 쪽은 담당자용 사유에 표시한다. 검증에 성공했지만 잡음
기준을 넘은 결과는 전북AI 판독을 유지하고 담당자 화면에 참고 메모를 붙인다. 값을 출력하는
도구는 `engine_v2/tools/privacy.py`의 공용 마스커를 쓴다.

가상 값만 넣은 합성 표 이미지로 `OCR:`와 `Table Recognition:`을 각각 호출해 HTTP 200을 확인했다.
`OCR:` 응답은 `choices[0].message.content`의 일반 문자열이며 줄 사이를 개행으로 나눴고,
좌표나 bbox는 없었다. 표 작업 응답도 문자열이지만 HTML이 아니라 `<fcel>`, `<lcel>`,
`<ecel>`, `<ucel>`, `<xcel>`, `<nl>` 구조 토큰을 사용했다. 합성 표의 OTSL을 격자로
변환해 가로·세로 병합을 복원하고 기존 `JBAITable`의 `rowspan`/`colspan`으로 보존한다.
응답에 쓸 만한 별도 reasoning 필드는 없었다. 합성 호출은 각각 약 0.6초 걸렸다.
`python -m engine_v2.tools.extract_check <합성.pdf> --doc resident_abstract --engine jbai --gt <정답.json>`로
합성 재생 결과를 점검할 수 있다. 실제 서류는 `JBAI_ALLOW_REAL_DOCS=true`를 명시하기 전에는 차단된다.
기관 제공 엔드포인트의 실제 응답 구조만 가려 확인할 때는
`python -m engine_v2.tools.jbai_dump <파일.pdf>`를, 합성·승인 자료의 요청 방식 지표를 비교할 때는
`python -m engine_v2.tools.jbai_bench <파일.pdf> --temperature-zero --gray-contrast --stripes 4 --dpi 300`을 쓴다.
두 도구 모두 실제 파일 실행 전에 `JBAI_ALLOW_REAL_DOCS=true`를 요구하며 응답 텍스트를 노출하지 않는다.

가려진 구조를 확인할 때는 다음처럼 실행한다. `jbai_dump`는 값이 가려진 응답 구조를 출력하고,
`jbai_bench`는 응답·이미지를 저장하지 않고 입력 방식별 숫자 지표를 출력한다. 두 도구는
이름·주소·번호의 한글·한자·숫자 등을 가린다.

```bash
set -a; source .env; set +a
JBAI_ALLOW_REAL_DOCS=true python -m engine_v2.tools.jbai_dump "<파일 경로>"
JBAI_ALLOW_REAL_DOCS=true python -m engine_v2.tools.jbai_bench "<파일 경로>" --temperature-zero --gray-contrast --stripes 4 --dpi 300 --doc resident_abstract
```

실서류 주민등록초본 시험에서 전북AI 판독 검증을 통과하지 않아 로컬 OCR로 대체된 사례가
있다. 전북AI 응답에는 bbox가 없어 해당 결과에는 위치 정보가 없다.

비교 지표는 처리시간, 판독 검증, 정답 필드 일치 등이다. 실제 서류의 비교 결과와 값은
이 공개 문서에 기록하지 않는다. 서류별 엔진은 기관과 협의한 시험 범위에서 실측 비교해
결정한다.

### 발견: OCR 신뢰도 ≠ 정답 여부

실측에서는 글자 단위 신뢰도와 필드 정답 여부가 일치하지 않는 사례가 있었다.
**엔진이 내는 신뢰도만으로 판정하거나 라우팅하지 않는다.**

→ 가정 A8 폐기. 필드 신뢰도는 **검증 통과 여부로 산정**한다:

| 검증 | 예 | 통과 시 |
|---|---|---|
| 형식 | 실제 존재하는 날짜인가, 발급일이 미래가 아닌가 | + |
| 서류 내부 일관성 | 생년월일 ↔ 주민번호 앞자리, 같은 값의 반복 등장 | ++ |
| 입력값 일치 | 신청자 입력 생년월일·발급일과 일치 | ++ |

OCR 신뢰도는 동점일 때 보조 지표로만 쓴다. 상세 산정식은 6단계에서 정한다.

result = run(application_input)        # 담당자용 전체 (ApplicationResult)

## 데모 사이트 연결

데모의 OCR 체인은 시연용 고정 응답 다음에 **전북AI 판독**(`demo/backend/ocr/jbai.py`)을
연결하고, 실패하면 `ENGINE_V2_OCR` 선택값을 쓰는 **Tier1.5 로컬 판독**
(`demo/backend/ocr/localocr.py`)으로 대체한다.

```
Tier1 fixture → Tier1.2 JBAI → Tier1.5 LocalOcr (engine_v2) → Tier2 PdfText → Tier3 Upstage(스텁)
```

| 파일 | 누가 읽나 |
|---|---|
| 시연용 샘플(파일명 일치) | Tier1 |
| **지원되는 텍스트 레이어 없는 서류·사진** | **Tier1.2 JBAI** — 문서 종류별 판독기와 핵심 검증을 통과하면 사용. 실패하면 Tier1.5 로컬 OCR |
| 텍스트 PDF · 암호 PDF | Tier2 (경계 기준을 Tier2와 동일하게: 첫 쪽에 글자가 있거나 암호면 Tier2) |
| 서류 종류를 못 알아본 파일, OCR 엔진 없는 서버 | 기존 계층 그대로 |

데모 체인 순서는 시연 고정 응답 → 전북AI → 로컬 OCR(선택 엔진) → PDF 텍스트다.
전북AI가 필수 필드·쪽 완전성 등 문서별 판독 검증을 통과하지 못하면 로컬 OCR로 대체한다.
환각 점수만으로 결과를 버리지는 않는다. 검증을 통과한 결과에 잡음이 있으면 담당자
화면의 판독 엔진 줄에 참고 표시한다. 실제 초본 시험은 전북AI 검증에 실패해 현재 로컬
OCR로 대체되었다. own을 신청 화면 판독 체인의 기본 엔진으로 연결하는 작업은 진행 중이다.
독립 실행형 `engine_v2.engine.run` 기본값과 데모 어댑터의 암묵 기본값은 구분한다: engine_v2는
macOS 외에서 own을 기본으로 하고, 데모 어댑터는 own 연결을 마칠 때까지 macOS에서 Apple
Vision, 그 밖의 환경에서 EasyOCR를 기본으로 한다. 환경변수로 선택 엔진을 지정할 수 있다.

신청자 화면은 **본인인증 → 서식 작성 → 서류 업로드 → 확인 및 제출** 순이다. 원본 공고
서식 위에서 온라인 작성·서명하고, 서식 목록 위 다운로드 메뉴에서 작성한 서식 PDF 한 파일과
원본 HWP를 받는다. 두배적금 서식5는 종이 작성 후 스캔본 제출을 선택할 수 있다. 담당자는
신청자가 올린 원본 서류를 화면에서만 확인한다.

데모 필드로 넘기는 값: `성명`, `생년월일`, `발급일`, `전입일`(= 전북 연속 거주 시작일, 배점 '도 거주기간'의 근거), `주소변동내역`, `현주소시도`, `판독검증`(서류 내부 검증 n/9 통과) + 각 원본 좌표.

OCR 엔진: `ENGINE_V2_OCR` = `applevision` | `own` | `easyocr` | `paddle` | `off`. `engine_v2.engine.run`/CLI 기본값은 macOS=`applevision`, 그 외=`own`이다. 데모 체인은 시연 고정 응답 → 전북AI → 선택 로컬 OCR → PDF 텍스트 순이며, 데모 비macOS 암묵 기본값은 아직 EasyOCR다.

시나리오 검증은 저장소 루트에서 모든 시나리오를 끝까지 실행한다. 파일 이름 순서상 P11\~P15가 P2\~P9보다 먼저 오므로 실패해도 다음 파일로 계속 간다.

```bash
for f in demo/backend/tests/run_p*_scenarios.py; do echo "== $f"; python -m demo.backend.tests.$(basename "$f" .py) || echo "FAILED $f"; done
```

## 본인 서류 점검 방법

PDF를 다른 곳에 올리지 말고 **본인 PC에서**, **저장소 루트에서** 실행한다. 본인 서류는 `engine_v2/data/private/`에 둔다 (커밋 차단됨).

```bash
python -m pip install -r engine_v2/requirements.txt
python -m engine_v2.tools.inspect_pdf engine_v2/data/private/초본.pdf
```

- 텍스트 레이어 유무, 페이지 수, 이미지 수, 암호화 여부를 알려준다.
- 숫자는 전부 마스킹해서 출력하므로 결과를 팀에 공유해도 된다.
- `--dump` 옵션을 주면 단어별 좌표를 `data/private/`에 저장한다 (추출 규칙 설계용, 커밋 금지).
