# 담당자 화면 목업 데이터

담당자 심사 화면(`/` → 담당자 탭)은 접수된 신청 건이 하나도 없으면 빈 표가 된다.
시연에서 "다양한 사람이 신청하면 이렇게 보인다"를 보여주려면 데이터를 넣어야 하는데,
방법이 셋이다. **현재 구현된 것은 1번(프론트엔드 하드코딩)**이고, 2·3번은 나중에
필요해질 때를 위해 방법만 적어 둔다.

| | 방식 | 목록·정원·필터 | 건별 심사표 | 원본 뷰어·bbox | 승인/반려 영속 | 준비 비용 |
|---|---|---|---|---|---|---|
| 1 | 프론트엔드 하드코딩 **(현재)** | O | O | 대역 이미지 | 브라우저 메모리 | 없음 |
| 2 | 실제 신청 플로우로 시드 | O | O | O (실제 PDF) | O (DB) | 샘플 PDF 생성 + 수십 초 |
| 3 | DB에 직접 삽입 | O | O | X | O (DB) | 중간 |

## 1. 프론트엔드 하드코딩 — 현재 구현

파일: [`demo/frontend/src/pages/officer/mock-data.ts`](../frontend/src/pages/officer/mock-data.ts)

### 켜지는 조건

`demo/frontend/src/api.ts`의 담당자 API 래퍼가 전환한다.

- `?mock=1` — 강제로 켠다. 백엔드가 떠 있어도 목업을 본다.
- **자동** — 담당자 목록 API가 실패했거나 접수 건이 **0건**일 때 목업으로 넘어간다.
  필터를 걸어서 0건인 경우는 해당하지 않는다(실제로 그 조건에 건이 없는 것이다).
- `?mock=0` — 어떤 경우에도 목업을 쓰지 않는다. 실제 접수가 0건인 것을 확인해야 할 때.

목업이 켜지면 화면 상단에 노란 배너가 뜬다. 시연을 보는 사람이 실제 접수 건으로
오해하지 않게 하는 장치라 지우지 않는다.

### 무엇이 들어 있나

행을 손으로 적지 않고 **고정 시드 난수**로 만든다. 시군별 정원 대비 진행률과
커트라인이 뜻을 가지려면 2천 건 규모가 필요한데 손으로는 못 적는다. 시드가 고정이라
새로고침해도 같은 화면이 나온다 — 시연 대본을 쓸 수 있다.

- 14개 시군 × 읍·면·동, 30개 성 × 50개 이름 조합
- 약 28%는 이미 처리됨(서류 완비 확인·1차 선발·보류·반려)

**두배적금 (점수제)** — 약 1,500건. 시군별 배정 인원 × 접수 배수(도시 1.0~1.35배,
군 지역 0.5~0.9배). 점수는 배점 구간(`rules/scoring.py`)을 그대로 적용해 산출하고,
만점 8명·85~89점이 최빈인 종 모양이다. AI판정은 적합 85% / 부적합 4% / 확인필요 10%.

신청 1건마다 **업로드 서류 5종**이 붙는다 (`rules/required_docs._double_savings_checklist`
그대로). 앞 4종은 전원 공통이고, 마지막 ⑥ 근로확인서류만 근로유형에 따라 5종 중
1종으로 갈린다.

| 슬롯 | 서류 | 목록 컬럼 |
|---|---|---|
| `resident_abstract` | 주민등록초본 | 초본 |
| `nhis_payment` | 2025년 건강보험료 납부확인서 | 건보료 |
| `nhis_qualification` | 건강보험 자격확인서 | 자격확인 |
| `nhis_acquisition_loss` | 건강보험 자격득실확인서 | 자격득실 |
| `work_proof` | **근로유형별 1종** | 근로확인서류 |

근로유형 분포는 직장가입자 65% / 지역가입자·피부양자 15% / 사업소득 사업자 12% /
농업·임업 6% / 어업 2%다. 근로청년 사업이라 직장가입자가 두껍되, 목록의
`근로확인서류` 칸에 다른 서류명이 섞여야 그 칸이 무엇을 위한 것인지 보인다.
건강보험 **가입구분은 근로유형에서 따라 나온다** — 건보료 확인서에 "지역가입자"라고
찍혀 있는데 4대보험 가입내역 확인서를 낸 건은 말이 안 된다.

판독값은 전부 그 사람의 사실값(생년월일·주소·전입일·가구원수·보험료·취업일)에서
나온다. 심사표의 근거 문장이 같은 날짜들에서 역산되므로, 서류가 다른 값을 보이면
심사표와 원본이 어긋난다. 심사 항목마다 근거 서류도 다르다 — 소득은 건보료
확인서, 거주기간·연령은 초본, 근로기간은 자격득실확인서의 취득일이다.

약 12%의 건은 서류 1종이 **아예 없다**(미제출). 전건 완비면 목록의 `미제출` 칸이
한 번도 안 보여서, 그 컬럼이 무엇을 위한 것인지 시연에서 드러나지 않는다.

**취업지원패키지 (선착순)** — 430건, 지원 항목 628회차. 이 사업은 **점수표가 없다.**
담당자가 보는 것은 "신청한 항목마다 필요한 서류가 왔는가, 그 서류가 인정 기간 안의
것인가"뿐이라, 목업도 그 축으로 만든다. 자세한 것은 아래 별도 절에 적었다.

### 취업지원패키지 — 무엇을 재현하는가

출처는 「2026년 전북청년 취업지원패키지 사업계획」 원문이다.

| 값 | 사업계획서 | 목업 |
|---|---|---|
| 신청기간 | 1차 2026.4.6.~5.1. / 2차 9.7.~10.2. | 1차 74% · 2차(9.7.~9.16. 접수 중) 26% |
| 지원규모 | 총 900건 (= 성과목표 330+20+150+400) | 항목 628회차 (69.8%) |
| 서류 인정 기간 | **※ 2026. 1. 1. 이후의 서류만 인정** | 판정의 축. 아래 참조 |
| 보완 | 7일 내 보완, 미보완 시 후순위자 선정 | 1차 건은 기한 종료 / 2차 건은 D-1~D-7 |
| 지원 항목 | 면접비 5만(정액·2회) / 정장 5만(실비·2회) / 사진 2만(실비·1회) / 자격증 5만(실비·2회) | 성과목표 비율로 가중 선택, 복수선택 |
| 자격요건 | 나이(18~39세)와 거주지뿐 | 소득·근로 요건 없음 |

서류는 사업계획서 「신청서류」 표 그대로다. **건강보험 서류는 한 장도 없다** —
그것은 소득요건이 있는 두배적금 쪽 서류다.

| | 공통서류 | 추가서류 |
|---|---|---|
| — | ①신청서(작성본) ②주민등록초본 ③통장사본(계좌 입력으로 갈음) | |
| 면접비 | | 면접확인서 |
| 면접정장비 | | 면접확인서 + 결제영수증 |
| 면접사진비 | | 면접용 사진사본 + 결제영수증 |
| 자격증 응시료 | | 응시확인서 또는 성적표(응시일 표기 필수) + 결제영수증 |

### 목록 화면도 사업에 따라 달라진다

표의 헤더와 셀이 **같은 배열**(`list.columns`)을 따른다. 예전에는 헤더만 서버가 주는
컬럼을 쓰고 셀은 `ApplicationList.tsx`에 하드코딩돼 있어서, 컬럼을 바꾸면 헤더와 값이
어긋났다. 지금은 `Cell` 컴포넌트가 컬럼 키로 분기한다.

| | 두배적금 (점수제) | 취업패키지 (선착순) |
|---|---|---|
| 순위 칸 | 순위 (시군 내 고득점순) | **순번** (접수 순서) |
| 5번째 컬럼 | 점수 | **신청 항목** ("면접비 2회 · 자격증 응시료 1회") |
| 서류 컬럼 | 초본·건보료·자격확인·자격득실·근로확인서류·기타 | 없음 (항목 회차마다 서류가 늘어 고정할 수 없다) |
| 정원 배지 | 시군별 배정 인원 대비 진행률·커트라인 | 없음 (선착순 접수 진행률 배지가 대신) |
| 정렬 | 점수순 / 접수순 | 접수순만 |
| 상세 화면 | 심사표(서식6) 패널 | 항목별 지급 내역 + 7일 보완 기한 |

`items_label`과 `rank_label`은 백엔드가 아직 보내지 않는 선택 필드다. 없으면 각각
`-`와 `순위`로 떨어지므로 실데이터 경로는 그대로 동작한다.

#### 서류 컬럼 (`doc:*`)

`미비서류` 개수 바로 뒤에 서류 종류마다 한 칸씩 온다. 개수를 보고 "어디가
걸렸나"로 눈이 이어지는 순서다. 칸을 누르면 상세 심사 화면이 **그 서류 탭을 연
채로** 열린다 (`onOpen(applicationId, slotKey)` → `ReviewDetail.initialSlotKey`).

- 고정 4칸(초본·건보료·자격확인·자격득실)은 헤더가 서류명을 쥐므로 **상태 점만** 찍는다
- `근로확인서류`와 `기타` 칸만 서류명을 같이 찍는다 — 사람마다 다른 칸이라 이름이 없으면 무슨 서류인지 알 수 없다
- `기타`는 고정 컬럼에 안 잡히는 것을 받는다: 행정기관 기간제의 근로계약서, 복수 사업장의 2번째 근로확인서류, 자필 서식5, 어느 슬롯에도 못 붙은 병합 페이지. **이 칸이 없으면 체크리스트에 슬롯이 늘 때 그 서류가 목록에서 조용히 사라진다**
- 안 낸 서류는 속 빈 회색 점이고 눌리지 않는다 (열 원본이 없다)
- 사업 필터가 `전체`일 때 섞이는 취업패키지 행은 이 칸들이 `—`다

**목록의 `미비서류` 숫자와 서류 칸은 한 계산에서 나와야 한다.** 백엔드는
`api/officer._doc_cells`가 `(칸들, 미비 개수)`를 한 쌍으로 반환하고, 목업은
`savingsDocCells`가 같은 규칙을 따른다. 따로 계산하면 "미비 3건인데 빨간 칸은
2개"인 표가 되고, 그런 표는 담당자가 더 이상 믿지 않는다.

미비 개수는 **1단계 서류 판정(`stage1_status`)만** 센다. 소득 140% 초과나 도외
주소 같은 2단계 자격 사유는 서류의 흠이 아니므로, 목업에서도 판독 결과에 근거로만
남기고 서류 판정은 건드리지 않는다. 그래서 "AI판정 부적합인데 미비서류 0건"인 행이
정상적으로 존재한다 — 서류는 다 멀쩡한데 자격이 안 되는 경우다.

### 불인정 사유 — 실제 심사 사례를 옮긴 것

목업이 만드는 판정 사유는 **실제 심사에서 나온 반려 사유**를 옮긴 것이다. 가공한
예시가 아니라 담당자가 적어 낸 문장이라, 목업이 이것을 재현하지 못하면 화면을
아무리 채워도 "실제로 무엇을 보는 화면인지"를 보여주지 못한다.

| 코드 | 사유 | 서류 | 판정 |
|---|---|---|---|
| `ISSUED_BEFORE_CUTOFF` | 결제일 251222 / 251231 / 251217 / 251226, 초본이 25년도 | 영수증·초본 | 부적합 |
| `WRONG_DOC_TYPE` | 등본 제출 (초본 필요) | 초본 | 부적합 |
| `DOC_NOT_SUBMITTED` | 초본 없음 | 초본 | 부적합 |
| `OUT_OF_REGION` | 초본 주소가 대전광역시 등 도외 | 초본 | 부적합 |
| `RRN_UNREADABLE` | 주민등록번호 표기 수정 필요 | 초본 | 확인필요 |
| `ITEM_NOT_SELECTED` | 신청분야 체크 누락 | 신청서 | 부적합 |
| `CONSENT_UNCHECKED` | 개인정보 동의서 체크 누락 | 신청서 | 부적합 |
| `ACCOUNT_HOLDER_MISMATCH` | 통장 사본 예금주가 본인이 아님 | 신청서(계좌) | 부적합 |
| `NOT_A_RECEIPT` | 접수확인서는 영수증을 대신할 수 없음 (결제일 명시 필요) | 영수증 | 부적합 |
| `EXAM_DATE_MISSING` | 응시확인서에 응시일 표기 없음 | 응시확인서 | 부적합 |
| `TRANSFER_PAYEE_UNVERIFIED` | 계좌이체 — 입금계좌 예금주가 업체 대표인지 증명 필요 | 영수증 | 확인필요 |
| `AMOUNT_MISMATCH` | 영수증 금액이 정가의 2배 (전산세무 2급 3만원 ↔ 6만원) | 영수증 | 확인필요 |
| `PAID_AFTER_EVENT` | 결제일이 응시일·면접일보다 뒤 (오픽 시험 260411 / 결제 260429) | 영수증 | 확인필요 |
| `RENTAL_VS_PURCHASE` | 정장 결제일 2/1 · 면접일 3/26 — 기본 대여 3박4일과 간격이 커 구입으로 보임 | 영수증 | 확인필요 |
| `EXAMINEE_UNIDENTIFIABLE` | 성적표(오픽 등급표)에 응시자 성명이 없어 본인 확인 불가 | 성적표 | 확인필요 |
| `EXAM_AFTER_APPLY_PERIOD` | 모집기간(4월) 이후 응시 (5/16) | 응시확인서 | 확인필요 |
| `PART_TIME_INTERVIEW` | 아르바이트 면접 — 지원 대상 여부 확인 | 면접확인서 | 확인필요 |

결과 분포는 적합 55% / 부적합 26% / 확인필요 19%다.

판정은 서류 판정의 합이다 — 한 장이라도 부적합이면 건 전체가 부적합이고,
미비서류 수는 적합이 아닌 서류의 장수다. 영수증이 인정되지 않은 회차는 지급액을
**미확정**으로 두고, 금액은 읽혔지만 확인이 필요한 회차(정가 불일치·예금주 불명)는
금액을 살려 두되 "영수증 확인 필요"를 붙인다.

### 동작하는 것 / 안 하는 것

동작한다:

- 역할 전환 3계층(읍·면·동 → 시군 → 도)과 역할별 보이는 범위·가능한 액션
- 사업·시군·읍면동·처리상태·AI판정·신청일 필터, 점수순/접수순 정렬, 페이지네이션
- 시군별 정원 대비 진행률 배지와 커트라인(120% / 100%), 선착순 사업 접수 진행률 배지
- 두배적금: 건별 심사표(서식6) 4항목과 근거 문장
- 취업패키지: 선착순 순번, 항목별 지급 내역과 계산 근거, 7일 보완 기한 카운트다운
- 자격요건·제외대상 체크리스트 (사업마다 항목이 다르다)
- 승인·반려·보류(일괄 포함) — **브라우저 메모리에만** 남는다. 새로고침하면 되돌아간다
- 근거 클릭 → 좌측 원본 하이라이트. 원본은 신청자 판독값을 박아 만든 **대역 SVG**다
- 목록의 서류 칸 클릭 → 상세가 그 서류 탭을 연 채로 열림 (두배적금 건은 좌측 탭이 5개다)

동작하지 않는다:

- 실제 업로드 PDF·OCR 결과 (대역 이미지로 갈음)
- 복수 사업장 근무자의 `work_proof_1`·`work_proof_2` 분기 (서버에는 있고 목업은 1개 사업장만 만든다)
- 작성 서식 PDF 내보내기 탭 (`forms`는 빈 배열)
- 판단의 DB 영속

### 상수를 서버와 맞춰야 한다

`mock-data.ts`는 시군별 정원·배점 구간·동점자 키·역할 정의를 **서버에서 복사해**
들고 있다. 아래 파일이 바뀌면 목업도 같이 고쳐야 한다. 어긋나면 목업을 보고 내린
판단이 실제와 달라진다.

- `demo/backend/rules/programs.py` — `DOUBLE_SAVINGS_QUOTA`, 신청기간, `document_cutoff`, 총 지원 규모
- `demo/backend/rules/scoring.py` — `INCOME_BANDS` / `RESIDENCE_BANDS` / `WORK_BANDS` / `AGE_BANDS` / `tiebreak_key`
- `demo/backend/rules/subsidy.py` — `LIMITS`(항목별 한도·횟수·실비 여부), `PERFORMANCE_TARGETS`, 추가서류
- `demo/backend/rules/roles.py` — `ROLES` (역할명·단계·액션 라벨)
- `demo/backend/rules/required_docs.py` — `_double_savings_checklist`의 슬롯 키·순서, `WorkCategory` 5종, `_work_proof`의 서류명 문구
- `demo/backend/api/officer.py` — `DOC_COLUMNS`(서류 컬럼 키·표기), `DOC_SHORT_BY_TYPE`(칸의 짧은 이름), `DOC_STATE_LABELS`, `_doc_cells`의 미비 개수 규칙

목업의 대응물은 `SAVINGS_DOC_COLUMNS` / `SAVINGS_SLOT_ORDER` / `WORK_PROOF` /
`DOC_STATE_LABELS` / `savingsDocCells`다. 컬럼 개수·순서·라벨이 서버와 어긋나면
목업 화면과 실데이터 화면이 **다른 표**가 되고, 그러면 목업으로 시연한 것이
실제로 되는지 아무도 확신할 수 없다. `?mock=1`과 `?mock=0`을 나란히 열어 보는
것이 가장 빠른 확인이다.
- `demo/backend/api/officer.py` — `LIST_COLUMNS`, `AI_STATUS_LABELS`, 필터 적용 순서

### 목업이 백엔드와 일부러 다르게 하는 것

선착순 사업에서 세 가지는 백엔드 동작을 그대로 따르지 않았다. 셋 다 백엔드가
그렇게 바뀌는 편이 맞다고 보고 목업이 먼저 그렇게 한 것이라, 옮길지 말지는
판단이 필요하다.

1. **순위 칸** — `api/officer._rank_by_region()`은 점수제 순위만 매겨 선착순 건의
   순위를 비운다. 목업은 **접수 순번**을 넣는다. 점수가 없는 사업에서 그 칸에 들어갈
   값은 "몇 번째로 들어왔는가"뿐이고, 예산 소진 시점을 가늠하는 근거도 그것이다.
2. **선착순 진행률의 분모·분자** — `_first_come_summary()`는 **신청 건수**를 센다.
   지원규모 900건은 성과목표 4종의 합(330+20+150+400)이라 **항목 건수**로 읽는 것이
   맞고, 신청 1건이 항목을 복수로 고르므로 둘은 다른 값이다. 목업은 항목 건수를 센다.
3. **시군별 정원 배지** — 백엔드는 필터와 무관하게 늘 내려보낸다. 목업은 선착순
   사업을 고르면 이 배지를 **비운다**. 시군별 배정 인원은 두배적금에만 있는
   개념이라, 취업패키지 목록 위에 띄우면 담당자가 지금 보는 목록의 진행률로 읽는다.
4. **목록 컬럼** — 백엔드의 `LIST_COLUMNS`는 사업과 무관하게 고정이라 선착순
   사업에서도 점수 칸이 온다(전건 비어 있다). 목업은 그 자리에 신청 항목을 넣고,
   순위 칸 라벨을 "순번"으로 바꾼다. 백엔드가 `items_label` / `rank_label`을
   보내기 시작하면 화면은 고칠 것이 없다.

## 2. 실제 신청 플로우로 시드 (미구현)

신청자 화면이 하는 일을 스크립트가 API로 그대로 수행한다. **화면의 모든 기능이
실제로 동작하는** 유일한 방법이다 — 원본 PDF가 실제로 있고, OCR이 실제로 돌고,
bbox가 실제 판독 좌표이고, 승인/반려가 DB에 남는다.

`demo/backend/tests/run_p4_scenarios.py`의 `seed()`가 이미 이 일을 4건 규모로 한다.
시드 스크립트는 그것을 규모만 키운 것이 된다.

### 방법

1. 샘플 PDF를 만든다 (저장소에 커밋되지 않는다).

   ```bash
   PYTHONIOENCODING=utf-8 PYTHONUTF8=1 python -m demo.fixtures.make_samples
   ```

2. `demo/backend/seed.py`를 새로 만들어, 건마다 아래를 호출한다.

   ```
   POST  /api/applications                       사업 선택
   PATCH /api/applications/{id}                  서식1 (이름·주소·생년월일·취업일…)
   POST  /api/applications/{id}/self-check       서식2 자가진단
   POST  /api/applications/{id}/consents         서식3·4·5 동의 + 전자서명
   PUT   /api/applications/{id}/doc-context      근로유형·사업장 수
   POST  /api/applications/{id}/documents        구비서류 업로드 (슬롯별)
   POST  /api/applications/{id}/submit           제출 → 엔진 파이프라인 + 채점
   ```

3. `fastapi.testclient.TestClient(app)`을 쓰면 서버를 띄우지 않고 같은 경로를 탄다
   (P4 검증 스크립트와 같은 방식). 다만 **`demo/demo.db`와 `demo/storage/`를 실제로
   건드리므로** 시드 전용임을 스크립트 상단에 명시하고, 되돌리기는
   `python -m demo.backend.reset`으로 한다.

### 주의할 점

- **점수가 잘 안 벌어진다.** 소득(40점)과 거주기간(25점)은 초본·납부확인서 **판독값**이
  근거라(`rules/facts.py`: 서류 판독값 우선) 같은 샘플 파일을 쓰면 전건이 같은 값이 된다.
  변별력은 서식1에서 오는 연령(10점)·근로기간(25점)뿐이다. 점수를 벌리려면 소득·전입일이
  다른 샘플 PDF를 여러 벌 만들어야 한다.
- 건당 업로드 5건 + OCR + 파이프라인이라 수백 건이면 수십 초~수 분 걸리고,
  `demo/storage/`에 파일이 그만큼 쌓인다.
- 시군별 정원(전주 550명)을 채우려면 수천 건이 필요한데, 그 규모는 이 방식으로는
  현실적이지 않다. 정원 배지를 실감나게 보여주는 것이 목적이면 1번이나 3번이 맞다.

## 3. DB에 직접 삽입 (미구현)

`Application` + `Review` 행을 만들어 `demo/demo.db`에 바로 넣는다. 업로드·OCR을
건너뛰므로 수천 건도 순식간이고, 점수 분포를 원하는 대로 만들 수 있다. 판단이 DB에
남는 것도 1번과 다른 점이다.

### 방법

```python
from demo.backend.models import Application, Review, get_session, STATUS_SUBMITTED
from demo.backend.rules.scoring import ScoringFacts, score_application, tiebreak_key
from demo.backend.rules.programs import DOUBLE_SAVINGS, get_program

program = get_program(DOUBLE_SAVINGS)
facts = ScoringFacts(
    household_size=4, monthly_premium=240_000, insurance_type="직장",
    transfer_in_date=date(2019, 4, 2), employment_date=date(2022, 8, 1),
    birth_date=date(1996, 5, 12),
)
sheet = score_application(
    facts,
    announcement_date=program.announcement_date,
    age_basis_date=program.age_basis_date,
)

with get_session() as s:
    app = Application(
        application_no="DS-2026-000001",
        program_code=DOUBLE_SAVINGS,
        status=STATUS_SUBMITTED,
        form1_json={"name": "홍길동", "address": "전북특별자치도 전주시 완산구 효자동 123", ...},
        self_check_json={str(i): "예" for i in range(1, 9)},
        submitted_at=datetime(2026, 3, 5, 9, 12),
    )
    s.add(app); s.commit(); s.refresh(app)
    s.add(Review(
        application_id=app.id,
        final_status="PASS", stage1_status="PASS", stage2_status="PASS",
        score_json=sheet.as_dict(), total_score=sheet.total, tiebreak_json=sheet.tiebreak,
        review_payload_json={...},   # 담당자 화면의 '최종 판정' 패널이 읽는다
    ))
    s.commit()
```

### 주의할 점

- **미비서류 수가 전건 부풀려진다.** `api/officer._missing_count()`가 체크리스트의
  필수 슬롯을 훑는데 `Document` 행이 하나도 없으므로 필수 서류 수(두배적금 5건)가
  그대로 미비 수가 된다. 목록의 "미비서류" 컬럼이 전부 5가 된다.
- **건별 원본 뷰어가 빈 화면이 된다.** 심사 상세는 `documents[0]`이 없으면
  "심사 정보를 불러오는 중…"에서 멈춘다(`ReviewDetail.tsx`의 `if (!detail || !activeDoc)`).
  최소 1건의 `Document` 행과 실제로 열리는 `file_path`가 필요하다.
- 시군·읍면동은 `form1_json["address"]` 문자열에서 파싱된다(`rules/facts.extract_region`).
  주소 문자열이 `전북특별자치도 {시군} {읍면동} {번지}` 꼴이어야 목록 컬럼이 채워진다.
- 신청번호는 `api/applications._next_application_no()`가 전체 건수로 매기므로, 직접
  삽입한 건과 화면에서 만든 건의 번호가 겹칠 수 있다. 시드는 별도 접두어를 쓰는 편이 안전하다.
